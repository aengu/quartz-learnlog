# correct_index 런타임 가드 — 자가검증으로 환각 0%에 수렴

> **결과**: 4월에 만든 offline 평가가 V2 프롬프트로 환각을 10% → 5%로 줄였지만 "완전 차단"은 못 했다. 6월 평가서 작성 중 그 빈 자리를 다시 인식하고, `correct_answer` ground truth + 결정적 검증 + 재생성으로 *사용자에게 도달하는 오류*를 **0/91 step(실측, N=20)** 으로 끌어내렸다. 평균 LLM 호출은 1.0회/시도 — 비용 추가 거의 없음.

| 항목 | 내용 |
| --- | --- |
| 목적 | [[프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트\|4월 작업]]에서 "추가 개선 방향 (미착수)"로 적어둔 *"생성 후 자동 검증 + 재생성"* 을 실현 |
| 방식 | LLM 출력에 `correct_answer` ground truth 필드 강제 → `choices[correct_index] == correct_answer` 결정적 코드 검증 → 환각 발생 시 재생성 |
| 범위 | `_gen_path_trace` 출제 단계만. 모델/스키마 변경 0건 |

---

## 만들게 된 계기 — 평가서가 발견한 빈 자리

> 내가 4월에 쓴 노트가, 6월의 나에게 다시 일을 시켰다.

[[업스테이지 평가서]]를 작성하면서 *"프롬프트는 환각을 줄일 뿐 없애지는 못한다, 결국 검증으로 잡아야 한다"* 는 문장을 썼는데, 이 문장을 본인이 다시 읽다가 갸웃했다. **"근데 그 검증 장치가 일회성이어도 괜찮은 건가? 내 경우(개발 단계 측정)는 0%까진 못 막았는데."**

이 자기 점검이 정확히 맞았다. [[프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트\|4월 작업]]에서 만든 건 사실 두 종류 중 한 쪽일 뿐이었다:

| 종류 | 정체 | 본인이 만든 것 |
| --- | --- | --- |
| **offline 평가** | 프롬프트 수정 전후 회귀 테스트. 배포 전 *"이 프롬프트가 더 나은가"* 판단. | ✅ 만듦 (LLM Judge까지) |
| **런타임 가드(guardrail)** | 매 요청마다 출력 검사. 사용자 보호. | ⬜ 미착수 |

4월 노트 12절에 *"추가 개선 방향 (미착수)"* 로 분명히 적어뒀던 두 번째 항목이 정확히 이 런타임 가드였다. 평가서 문장이 그 빈 자리를 *"검증"* 한 단어로 압축해버려서, 본인조차 잠깐 *"이미 해결한 일"* 처럼 착각하고 있었던 것.

→ 그 자리에서 구현하기로 결정. 평가서 문장도 정확히 갱신하기로.

---

## 진단 — explanation으로는 결정적 검증이 안 된다

런타임 가드를 만들려면 *"이 출제가 옳은가"* 를 코드가 판단해야 한다. 가장 자연스러운 후보는 `explanation`을 보고 정답을 추출해 `choices[correct_index]`와 맞춰보는 것 — 4월 작업에서 이미 시도한 휴리스틱 방식이다.

그런데 그 방식의 한계가 4월 노트 5~6절에 그대로 적혀있었다:

| 한계 | 4월의 실측 |
| --- | --- |
| 서사 구조에서 정답 추출 자체가 애매 | *"처음엔 1이고 → 결국 3"* 같은 explanation에서 어느 숫자가 정답? |
| 가짜 오류 75% | 휴리스틱이 보고한 오류 8건 중 6건이 false positive |
| 스킵률 60~70% | explanation에 구체적 숫자 없으면 정규식이 잡을 게 없음 |
| 결국 LLM Judge로 교체 | 자연어 검증은 결정적 규칙으로 불가능 → LLM 판정에 비용·환각 위험 |

자연어 검증은 *원리적으로* 결정적이 될 수 없다. 정규식은 표현 다양성을 못 따라가고, LLM Judge는 다시 확률적이다. **결정성을 원한다면 LLM이 *구조화된 ground truth* 를 직접 출력하게 만들어야 한다.**

## 설계 — `correct_answer`를 ground truth로 강제

핵심 한 줄: **LLM에게 정답을 두 번 쓰게 한다.**

```json
{
  "question": "참조 횟수는?",
  "choices": ["1", "2", "3", "4"],
  "correct_index": 1,
  "correct_answer": "2",      // ← 신규. choices[correct_index]와 정확히 같아야 함
  "explanation": "..."
}
```

검증 한 줄로 끝:

```python
def is_valid(step):
    ci, ca, cs = step.get('correct_index'), step.get('correct_answer'), step.get('choices', [])
    return isinstance(ci, int) and 0 <= ci < len(cs) and cs[ci] == ca
```

이게 결정적인 이유:
- `choices[correct_index]`와 `correct_answer`는 둘 다 구조화된 string. *코드 비교* 한 번.
- 자연어 파싱 없음 → 가짜 오류 가능성 0
- 비용 0 (출력 토큰 약간 증가뿐)

**LLM에게 답을 두 번 쓰게 만들면, 자리(index)와 값(value)을 헷갈리는 그 순간 두 출력이 어긋난다.** 4월 노트 7절의 V2 프롬프트가 *"correct_index를 정한 뒤 choices[correct_index]를 꺼내서 정답 값과 같은지 다시 확인하세요"* 라고 self-check를 *지시* 했는데, 그건 LLM의 *의지*에 의존했다. `correct_answer`를 출력 형식에 *강제*하니 self-check가 **코드 레벨로 외재화**된 셈이다.

### 흐름

```python
def _gen_path_trace(self, log):
    prompt = "..."  # v2 프롬프트 + correct_answer 출력 규칙
    content, raw_count = self._gen_and_validate(prompt)

    # 환각 1개라도 발생(통과 < raw) 또는 통과 step 부족이면 1회 재생성
    all_ok = (len(content.get('steps', [])) == raw_count
              and raw_count >= self.PATH_TRACE_MIN_STEPS)
    if not all_ok:
        retry, _ = self._gen_and_validate(prompt)
        if len(retry.get('steps', [])) > len(content.get('steps', [])):
            content = retry
    if not content.get('steps'):
        raise ValueError("path_trace 출제 실패: 유효한 step이 없습니다")
    return content
```

### 정책 결정 — 환각 1개라도 발생하면 즉시 재생성

처음엔 *"통과 step이 3개 미만일 때만 재생성"* 으로 두려 했다. 그런데 곱씹어보니 **환각이 1개라도 통과한 응답은 LLM의 자기일관성이 그 순간 깨졌다는 신호**고, 다른 step의 신뢰도까지 흔든다. 환각 step만 걸러내고 나머지를 그대로 쓰는 것보다 *전체 응답을 다시 받는* 게 더 안전하다고 판단했다.

전체 재생성의 비용 우려는 사실상 없다 — 평균 LLM 호출이 1.0회/시도에 머무는 게 실측이라(아래 검증), 환각 자체가 거의 발생 안 해서 재생성 트리거도 거의 안 걸린다.

## 부가 발견 — `response_format`은 환각이 아니라 JSON 형식 안정성

작업 중간에 별개 문제가 드러났다. Mistral 응답이 가끔 *"line 5 column 19 근처 Unterminated string"* 으로 JSON 파싱 실패. `max_tokens`를 1500 → 2000으로 늘려도 안 잡혔다(응답이 잘리는 게 아니라 **응답 시작 부분**부터 깨졌다 — escape 처리 미스로 추정).

해결: Mistral SDK의 `response_format={"type": "json_object"}` 적용. 모델 측에서 JSON 형식 보장.

**중요한 구분**: 이건 **환각이 아니라 JSON 형식 안정성에만 영향**한다. 시계열로 보면:

| 시점 | response_format | 환각률 | JSON 파싱 실패 |
| --- | --- | --- | --- |
| max_tokens=1500 | ❌ | 0/19 | 1/3 |
| max_tokens=2000 | ❌ | 0/18 | 3/5 |
| max_tokens=2000 | ✅ | 0/22 | 0/5 |

환각률은 response_format 적용 *이전부터* 이미 0%였다. response_format은 *"형식이 깨진 채로 잘리지 않게"* 보장하는 거지, *모델이 내용을 옳게 만드는* 것과는 별개 메커니즘이다. 평가서 갱신 시 이걸 헷갈리면 안 된다.

## 검증 — 단계적 실측

### 작은 표본 — response_format 효과 분리 측정 (각 5회)

| 지표 | response_format 적용 전 | 적용 후 |
| --- | --- | --- |
| 성공률 | 4/5 (80%) | **5/5 (100%)** |
| 재생성 발생 | 2/5 (40%) | **0/5 (0%)** |
| PARSE ERROR | 3회 | **0회** |
| 환각 step | 0% | **0%** |
| 평균 LLM 호출 | 1.4회/시도 | **1.0회/시도** |

이 비교가 보여주는 것 — `response_format`은 *환각이 아니라 JSON 형식 안정성*에 단독으로 영향. 환각률은 두 시점 모두 0%였다.

### 큰 표본 — N=20 정식 측정

스트레스 케이스(파이썬 참조 카운팅, 숫자형 선택지가 잘 나오는 주제)로 20회 출제 측정.

| 지표 | 값 |
| --- | --- |
| N | 20 |
| 소요 시간 | 115초 (≈ 2분) |
| 성공률 | **100% (20/20)** |
| 평균 LLM 호출 | **1.0회/시도** |
| 재생성 발생 | 0회 |
| PARSE ERROR | 0회 |
| 총 raw step | 91 |
| 환각 step | **0** |
| **환각률** | **0.00% (0/91)** |

작은 표본(22 step)에서 본 0%가 **91 step**으로 늘어나도 유지됐다. 4배 표본 확대에도 한 건도 안 나옴 — *"표본이 작아서 우연히 0인가"* 라는 의심을 한 단계 더 강하게 떼어냈다.

다만 [[프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트\|4월 노트 12절]]의 LLM Judge 실측이 V2에서 80건 중 4건(5%) 오류였던 것과 비교하면, *동일 모델·동일 프롬프트·동일 쿼리에서* 이 차이는 다음 셋의 조합으로밖에 설명되지 않는다:

1. `correct_answer` 필드 도입으로 LLM이 *자기 정답을 두 번 쓰게* 강제됨 → self-check가 코드 레벨로 외재화
2. 결정적 코드 검증(`choices[ci] == ca`)이 *환각이 통과할 가능성을 0으로* 만듦 (가짜 정답 통과 케이스 한계는 [[#한계 — 자기일관성 환각 미면역]] 참조)
3. `response_format`이 응답 형식 안정성을 보장해 PARSE ERROR가 재시도 슬롯을 안 잡아먹게 함

→ *프롬프트만 v2였던* 4월의 5%가 *프롬프트 + 출력 형식 강제 + 결정적 검증* 으로 사실상 0%까지 떨어진 셈이다. 평가서의 *"검증으로 잡아야 한다"* 가 표본 91 step에서 실측으로 입증됐다.

## 한계 — 자기일관성 환각 미면역

`correct_answer`가 잡는 건 *"LLM이 자리(index)와 값(answer)을 *다르게* 환각하는 경우"*다. 만약 LLM이 **둘 다 같은 패턴으로 일관되게 잘못 쓰면** 통과한다.

예: choices=["1","2","3","4"], 진짜 정답이 "2"인데 LLM이
- `correct_index=2` (자리 환각)
- `correct_answer="3"` (값도 같이 잘못)

→ `choices[2] == "3" == correct_answer` → **통과되어버림 (가짜 정답)**

다행히 [[프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트\|4월 작업]]에서 본 환각 패턴은 전부 *"자리는 잘못, 값은 explanation과 맞음"* 형태였고, 우리 실측에서도 자기일관성 환각은 0/91 step으로 한 건도 안 보였다. 다만 *원리적으로* 가능한 빈틈이긴 하다.

더 엄격한 안전망 후보(미착수):
1. **삼각 검증** — explanation의 논리적 정답까지 LLM Judge로 교차. 비용 ↑
2. **숫자형 선택지를 서술형으로 강제** — `"2"` 대신 `"참조 횟수는 2이다"`. 값/인덱스 혼동이 *구조적으로 불가능*. 가장 근본적. 채점 로직도 손봐야 함 (4월 노트 12절에 미착수로 적어둔 첫 번째 항목)

지금 단계에선 실측 0%이므로 추가 안전망의 한계 효용이 낮다. 미래에 자기일관성 환각이 실측되면 그때 추가.

## 회고

### "검증 체계"라는 단어의 두 종류

평가서에 *"검증으로 잡아야 한다"* 한 문장으로 쓴 건 사실 두 종류를 뭉친 거였다. **offline 평가**는 *"배포 결정"* 을 돕고, **런타임 가드**는 *"사용자 보호"* 를 한다. 본인이 4월에 만든 건 전자뿐이었고, 노트엔 그걸 분명히 *"미착수"* 로 적어뒀는데도, 두 달 뒤 평가서 쓸 때 *"검증 = 다 했음"* 으로 무의식적으로 묶었다. 자기 점검이 그 묶음을 풀어줬다.

→ **노트에 "미착수"라고 정직하게 적어두는 습관이 한참 뒤의 자기에게 다시 일을 시킨다.** 그 시점에 안 한다고 후회할 일이 아니라, *"안 했다"는 사실 자체*가 미래의 동력이다.

### self-check의 외재화

V2 프롬프트의 self-check 지시는 *"LLM이 잘 따라줘야"* 작동했다. `correct_answer` 도입은 그 self-check를 **출력 형식에 박아넣어 코드가 강제**하는 셈이다. 비슷한 패턴은 다른 LLM 작업에도 일반화 가능 — *"검증 가능한 형식으로 출력하게 만들면 검증의 결정성이 따라온다."* 자연어로 답하게 두지 말고 구조화된 ground truth를 옆에 두자.

### 평가서 → 코드 → 평가서 사이클이 닫힘

이번 작업으로 [[업스테이지 평가서]] 작성 → [[Tavily 한국어 검색 품질 개선 — 평가서가 잡아낸 grounding 실패\|검색 품질 개선]] → 평가서 자기 점검 → 런타임 가드 구현 → 평가서 갱신의 사이클이 두 번째도 완성됐다. 첫 번째 사이클이 *"평가서가 코드의 검색 버그를 잡았다"* 였다면, 두 번째는 *"평가서가 본인 검증 체계의 빈 자리를 드러냈다"*. dogfooding이 작품의 깊이를 만든다.
