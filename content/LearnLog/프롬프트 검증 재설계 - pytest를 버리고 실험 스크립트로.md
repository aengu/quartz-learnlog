## 프롬프트 검증 재설계 - pytest를 버리고 실험 스크립트로

| 항목 | 내용 |
| --- | --- |
| 목적 | 이전에 만든 `test_prompt_correct_index.py`를 재검토하고, 용도에 맞게 실험 스크립트로 재설계 |
| 방식 | pytest 골격 제거 → `search/experiments/` 모듈로 분리. baseline(OLD vs NEW 일회성) + regression(NEW 다중 쿼리) 2단 구조 |
| 범위 | `search/experiments/{_common,validate_baseline,validate_regression}.py` |

## 요약

- **목표**: learnlog의 Exercise(학습 문제) 생성 시 LLM이 틀린 `correct_index`를 만드는 버그를 프롬프트로 고치고, 그 효과를 수치로 검증.
- **한 일**: 예전 테스트 코드(pytest 기반)를 재검토 → 구멍이 많아서 실험 스크립트로 재설계. Groq 무료 티어 예산에 맞춰 2단 구조(baseline/regression)로 분리.
- **의외의 결과**: baseline 실행 결과 NEW 프롬프트가 *더 나빠 보였음*. 원시 데이터 까보니 "오류"의 약 절반 이상이 **검증 로직(휴리스틱) 자체의 false positive**. 진짜 문제는 프롬프트가 아니라 검증 로직이었다.
- **휴리스틱 개선 + 재분석 (API 0)**: 결론 지시어 + 마지막 매칭 방식으로 교체 후 같은 JSONL을 재분석 → OLD **4.3%** (1/23) vs NEW **9.7%** (3/31). 방향은 유지(NEW가 더 나쁨), 크기는 축소. 가설도 *"correct_index=2 앵커링"* → **"shifted choices에서 value-index 혼동"**으로 좁혀짐.
- **프롬프트 v2 (20 calls)**: 예시를 shifted choices로 교체 + ✅/❌ 양쪽 명시 + self-check 지시 추가. 결과 **3.3%** (1/30) — v1 대비 **−6.4%p**, OLD보다도 낫다. 가설이 수치로 증명됨.
- **다음 할 일**: regression 실험으로 v2가 다른 numeric 쿼리(binary_search, http_redirect)에서도 작동하는지 + 악화 케이스 없는지 확인 (예상 40 calls).

## 배경 — 뭘 하려고 이 실험을 만들었나

learnlog는 AI 답변을 학습 로그로 쌓고, 그걸 바탕으로 복습용 **Exercise(연습문제)**를 LLM이 자동 생성해주는 개인 학습 앱이다. 문제 유형 중 하나가 **경로추적(path_trace)** — 객관식으로 단계별 실행 흐름을 묻는 형식이다.

Exercise 한 step은 보통 이렇게 생겼다.

```json
{
  "question": "obj = []; ref = obj 이후 obj의 참조 횟수는?",
  "choices": ["1", "2", "3", "4"],
  "correct_index": 1,
  "explanation": "다른 변수가 같은 객체를 참조하면 횟수가 증가합니다. 따라서 참조 횟수는 2입니다."
}
```

채점 로직은 단순하다: 사용자가 고른 인덱스 == `correct_index` → 정답.

### 버그

LLM이 출제할 때 `correct_index`를 엉뚱한 값으로 넣는 경우가 보였다.

```json
{
  "choices": ["1", "2", "3", "4"],
  "correct_index": 2,           // ← 이게 잘못됨
  "explanation": "... 참조 횟수는 2입니다."
}
```

`explanation`은 "정답은 2"라고 말하는데, `choices[2]`는 `"3"`이다. 실제 정답 "2"는 `choices[1]`에 있으니 `correct_index`는 1이어야 맞다. LLM이 **"값 2"와 "배열의 2번째 자리"를 혼동**한 것.

이게 왜 치명적이냐면, 채점 로직은 `correct_index`를 그대로 믿기 때문에 **사용자가 정답을 골라도 오답 처리된다**. 출제 단계에서 틀어져 있으면 그 문제는 영영 풀리지 않는 문제가 된다.

### 두 단계의 작업

| 역할 | 하는 일 |
|------|---------|
| **프롬프트 개선** | 버그 자체를 고침 ("correct_index는 0-based 인덱스다" 같은 규칙 추가) |
| **검증 스크립트** | 프롬프트가 진짜 효과 있는지 수치로 증명 |

LLM은 확률적이라 "한두 번 돌려봐서는 모른다". 그래서 구/신 프롬프트 각 N회 돌려서 오류율을 비교하는 검증 스크립트가 필요했다. 이 문서는 그 **검증 스크립트를 재설계한 과정**이다.

관련 문서(버그 발견 경위 + 프롬프트 수정 및 초기 테스트): [[프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트]]

### 용어 정리

| 용어 | 뜻 |
|------|-----|
| OLD 프롬프트 | `correct_index` 규칙을 추가하기 **전**의 원래 프롬프트 |
| NEW 프롬프트 | 규칙을 추가한 **후**의 현재 프롬프트 |
| step | Exercise 안의 한 문항 (question + choices + correct_index + explanation) |
| 휴리스틱 | "완벽하진 않지만 대체로 맞는 규칙 기반 검증". 여기선 *정규식으로 explanation에서 정답 숫자를 뽑아 `choices[correct_index]`와 비교*하는 자동 채점 로직 |
| false positive | 휴리스틱이 "오류"라고 잘못 찍은 경우. 실제로는 LLM 답이 맞음 |
| baseline / regression | 이번에 만든 두 실험 스크립트. baseline = OLD vs NEW 일회성 비교 / regression = NEW만 다중 쿼리로 상시 검증 |

# Part 1. 설계

## 기존 테스트를 다시 본 이유

주요 기능 구현이 거의 끝나서 이제 검증에 집중하려고 했다. 그중에 눈에 걸린 게 전에 만든 `test_prompt_correct_index.py`. 그때는 "프롬프트 바뀐 효과를 숫자로 보여준다"는 목적 하나로 짰는데, 다시 보니까 테스트로서도 실험으로서도 어정쩡했다.

## 재검토에서 드러난 문제들

차례로 짚어보니 구멍이 꽤 많았다.

**1. assertion이 목적이랑 안 맞았다.**

```python
assert new <= old + 0.05
```

목적은 "오류가 *줄었는지*" 측정인데 assertion은 "*악화되지 않았는지*"만 본다. 개선이 0%여도 통과, 심지어 3%p 악화되어도 통과. 회귀 방지 용도로도 애매했다.

**2. 입력이 단 하나였다.**

파이썬 GC 쿼리 하나로만 돌렸다. 이 쿼리에서 잘 작동한다고 해서 SQL/알고리즘/HTTP 도메인에서도 잘된다는 보장은 전혀 없다. 프롬프트 일반화를 전혀 검증 못하는 구조.

**3. ground truth가 LLM 자신이었다.**

휴리스틱이 **LLM이 쓴 explanation에서 정답을 추출**해서 그걸 기준으로 `choices[correct_index]`가 맞는지 검증한다. 근데 LLM이 explanation부터 틀리게 쓰면 그 틀린 정답을 "진리"로 잡는다. **자기 참조적 검증.** (이게 나중에 가장 큰 문제로 드러난다.)

**4. 프롬프트가 프로덕션과 드리프트될 위험.**

`PROMPT_NEW`가 테스트 파일에 하드코딩되어 있어서, `services.py`의 실제 프롬프트를 수정해도 테스트는 옛날 버전을 검증한다. 동기화가 전부 수동.

**5. 스킵률이 너무 높아서 통계적 의미가 없었다.**

전체 step의 70%가 스킵되는 경우가 많았다(휴리스틱이 판단 불가로 분류). 20회 반복했어도 실제 검증된 step은 17~24개 수준. 이걸로 프롬프트 차이를 논하는 건 무리.

**6. pytest가 과했다.**

API를 실제로 때리는 테스트라 CI에서 못 돌리고, `@pytest.mark.slow` 붙여서 기본 실행에서 빠진다. 결국 수동 실행인데 그럼 굳이 pytest 안에 있을 이유가 없다.

## 방향 결정 - 회귀 테스트가 아니라 실험 스크립트로

두 가지 선택지가 있었다.

- **A. 일회성 실험 스크립트로**: pytest 제거, 리포트만 출력하고 끝. 프롬프트 확정되면 결과 남기고 폐기.
- **B. 회귀 테스트로**: 다중 쿼리 + 절대 기준 assertion으로 본격 테스트화.

결론은 **A 방향에 가까운 하이브리드**. 프롬프트가 아직 계속 수정될 여지가 있으니 완전한 B는 이르고, 그렇다고 A처럼 1회 쓰고 버리기엔 프롬프트 수정할 때마다 뭔가 돌려보고 싶으니까. 그래서 두 단계로 쪼갰다.

1. **baseline 스크립트** - OLD vs NEW를 한 번 비교해서 개선을 확정. 결과 JSON 남기고 OLD는 영구 폐기.
2. **regression 스크립트** - NEW만 다중 쿼리로 상시 검증. 프롬프트 수정할 때만 돌림.

pytest 골격은 완전히 제거. `search/experiments/`로 옮기고 `python -m search.experiments.validate_*`로 직접 실행.

## 예산이 설계를 결정했다

설계 방향을 잡자마자 부딪힌 건 Groq 무료 티어 한도였다. 전에 20회×2프롬프트=40 calls 돌린 거 두 번 연속이면 일일 한도 초과. 즉 **일 예산이 대략 40~70 calls**.

설계안별로 예산을 계산해봤다.

| 설계 | 쿼리 | 프롬프트 | N | 총 calls | 일 1회 실행 가능? |
|------|------|----------|---|----------|-------------------|
| 현재 | 1 | 2 | 20 | 40 | ✅ (아슬) |
| 다양화 + 비교 | 3 | 2 | 7 | 42 | ✅ |
| 다양화 + 비교 | 5 | 2 | 4 | 40 | ✅ |
| **비교 제거, 다양화** | **5** | **1** | **8** | **40** | ✅ |

핵심 깨달음: **N=4~8은 통계적으로 거의 무의미**하다. LLM random variance가 ±5~10%p는 쉽게 나와서 그 수준의 반복으로는 프롬프트 차이를 못 본다.

그래서 결론:

- **OLD vs NEW 비교는 1회 실행으로 확정**짓고 (1 쿼리 × 2 프롬프트 × 20회 = 40). 다양성 없는 대신 반복을 살림.
- **이후 회귀 검증은 다양성을 살리고 반복을 줄임** (5 쿼리 × 1 프롬프트 × 8회 = 40). 프롬프트가 *다양한 도메인에서 동작하는가*만 본다.

예산이 빠듯하니까 두 목표를 한 스크립트에 합치는 건 포기하고 쪼갰다.

## 최종 설계

### 파일 구조

```
search/experiments/
├── __init__.py
├── _common.py                # 쿼리 세트, 프롬프트 빌더, 검증기, Groq 실행기, 리포트

└── results/                  # JSONL/JSON 결과 누적
```

### 쿼리 세트 (5개)

LLM이 만들어내는 choices의 형태에 따라 휴리스틱이 두 가지 전략으로 갈라진다.

- **numeric choices**: `["0","1","2","3"]`처럼 전부 숫자형 → 직접 문자열 비교
- **descriptive choices**: `["참조 횟수 1로 유지", "참조 횟수 2로 증가", ...]`처럼 서술형 → 정답 숫자가 choice 문장에 포함되는지로 교차 검증

쿼리 세트는 숫자형 답(python_gc, binary_search, http_redirect)과 서술형 답(sql_btree_index, jwt_verification)을 섞었다. 둘 다 자극해야 쓸모있는 데이터가 나온다.

### 429 감지 + 즉시 중단

Rate limit 걸리면 `RateLimitHit` 예외로 배치를 즉시 중단하고, 지금까지 수집된 부분 결과로 리포트를 찍는다. 매 호출 직후 JSONL에 append하니까 크래시해도 데이터는 안 날아간다.

```python
class RateLimitHit(Exception): pass

def call_groq(client, prompt):
    try:
        response = client.chat.completions.create(...)
    except Exception as e:
        if any(h in str(e).lower() for h in RATE_LIMIT_HINTS):
            raise RateLimitHit(str(e)) from e
        return None, f"[API 에러] {e}"
    ...
```

### regression은 assertion 대신 경고

pytest 아니니까 assert 안 쓴다. 그 대신 오류율 15% 초과 시 콘솔에 ⚠️ 경고만. 숫자 보고 판단하는 건 결국 사람 몫.

```
─────────────────────────────────────────
  전체 오류율: 6.5%  (기준선: 15%)
  ✅ 기준선 이내.
=========================================
```

## 프롬프트 drift를 어떻게 막을 것인가

이 질문에서 한참 고민했다.

처음 생각은 **`services.py`에서 프롬프트 빌드 함수만 따로 빼서 실험에서 import하자**였다. 그러면 프로덕션 코드를 건드려야 하는 대신, 프롬프트가 항상 프로덕션과 일치한다.

```python
# services.py
def _build_path_trace_prompt(query, response) -> str:
    return textwrap.dedent(f"""...""").strip()

def _gen_path_trace(self, log):
    prompt = _build_path_trace_prompt(log.query, log.ai_response[:1000])
    return self._call_groq_json(prompt)
```

근데 OLD 프롬프트는 어차피 `_common.py`에 상수로 보존할 거다. OLD는 앞으로 안 바뀌니까 상수로 두는 게 자연스럽다. 여기서 일관성 문제가 생겼다.

- OLD는 상수로 OK
- NEW는 import해서 동기화

같은 파일에서 왜 둘이 다르게 취급받지? OLD가 상수로 괜찮다면 NEW도 그래야 한다. 트레이드오프만 있을 뿐.

- **import 방식**: 자동 동기화, 대신 프로덕션 코드 리팩토링 필요
- **상수 방식**: 단순, 대신 프롬프트 수정할 때 수동 동기화 필요

결론: 현재 프로젝트는 solo 개발이고, 프롬프트 수정하는 사람 = 검증 스크립트 돌리는 사람 = 같은 사람. drift 실수 여지가 크지 않다. 그리고 리팩토링이라는 게 "검증을 위해 프로덕션을 건드리는" 성격이라 배보다 배꼽이 더 크다.

그래서 **둘 다 상수**로 가되, 파일 상단에 명시적 경고 주석을 달았다.

```python
# _common.py
# ⚠️ build_new_prompt는 services.py의 _gen_path_trace 프롬프트와 동기화 유지 필수.
#     services.py 프롬프트 수정 시 반드시 아래 템플릿도 함께 수정할 것.
# build_old_prompt는 correct_index 규칙 추가 이전의 베이스라인 프롬프트 (고정, 수정 금지).
```

완벽한 해결책은 아니지만, 제약 조건 안에서는 제일 단순하다.

## 설계 단계의 한계 (실행 전 인지)

**1. 여전히 표본이 작다.**

예산 때문에 regression이 쿼리당 8회. LLM variance를 생각하면 이 수치로 프롬프트 차이를 엄밀하게 비교하는 건 어렵다. "큰 문제가 없는지" 점검하는 용도로만 봐야 한다.

**2. 검증 휴리스틱은 여전히 LLM 자기 참조다.**

`extract_answer_from_explanation`이 여전히 LLM 설명에서 정답을 뽑는다. 이걸 해결하려면 쿼리별로 *사람이 직접 만든 정답 세트*가 필요한데, 경로추적 문제는 매번 다른 시나리오로 생성되어서 고정된 gold set을 만들기 어렵다. 일단 유지. (이 결정이 나중에 뒤통수를 친다.)

**3. 프롬프트 수동 동기화 부담.**

`_common.py`에 프롬프트 상수를 둔 선택의 대가. 까먹으면 실험은 옛 프롬프트를 검증하게 된다. 주석 경고로 막았지만 잊을 가능성은 0이 아니다.

**4. Groq 무료 티어 제약 자체가 설계를 옭아맸다.**

예산이 풀리면 쿼리 10개 × 반복 30회 같은 구성이 가능하고, 그러면 결과의 신뢰도가 훨씬 올라간다. 지금 설계는 본질적으로 "예산 내 최선"이지 "이상적"은 아니다.

## 처음 세운 가설 — correct_index=2 앵커링

NEW의 5개 오류를 보자마자 패턴이 눈에 들어왔다.

```
iter5  step1: correct_index=2, choices=['1','2','3','4'], explanation 정답='2'
iter7  step0: correct_index=2, choices=['1','2','3','4'], explanation 정답='1'
iter8  step1: correct_index=2, choices=['1','2','3','4'], explanation 정답='2'
iter14 step0: correct_index=2, choices=['1','2','3','4'], explanation 정답='1'
iter15 step0: correct_index=2, choices=['1','2','3','4'], explanation 정답='1'
```

**5번 중 5번 다 correct_index=2**. 랜덤 노이즈가 아니라 체계적 bias. 원인 짐작이 바로 갔다.

NEW 프롬프트에 넣은 규칙의 예시 문장:
```
예: choices가 ["0","1","2","3"]이고 정답이 "2"이면 correct_index는 2입니다.
```

이 예시를 LLM이 **"correct_index는 2"라는 규칙**으로 흡수해버린 거 아닐까 — 프롬프트 엔지니어링의 고전 문제인 **example leakage**(예시가 정답이 되어버리는 현상). 이대로 결론 내고 v2 프롬프트 작업으로 넘어가려다가, 원시 데이터를 한 번 더 보기로 했다.

## 원시 데이터를 보고 난 진짜 반전

모든 API 응답은 호출 직후 JSONL 파일에 저장해놨다. 그걸 열어서 문제가 된 step들의 전체 내용을 보니까 분위기가 완전히 달라졌다.

### NEW iter7 step0 (휴리스틱이 "오류"로 잡은 케이스)

```json
{
  "correct_index": 2,
  "choices": ["1", "2", "3", "4"],
  "explanation": "객체가 생성되면 참조 횟수는 1입니다. 다른 변수가 같은 객체를 참조하면 횟수가 증가합니다. 또한 sys.getrefcount(obj) 함수 호출 시, 함수 인자로 임시 참조가 추가되어 ..."
}
```

휴리스틱은 explanation에서 **첫 번째 "횟수는 1"**을 잡아서 "정답=1"이라 판단했다. 그리고 `choices[2]='3' ≠ '1'`이니 "오류"라고 기록.

근데 **실제 질문의 답은 "3"**이다. `sys.getrefcount` 함수를 호출하면 함수 인자로 임시 참조가 +1 붙어서 결과가 3이 된다는 내용. `choices[2]='3'`, `correct_index=2`는 실제로 올바르다. **정답인데 휴리스틱이 착각해서 틀렸다고 찍은 것.** 이게 false positive다.

iter14, iter15도 같은 패턴 — explanation이 "객체 생성 후 참조는 1이지만, sys.getrefcount 때문에 결국 3이 된다"처럼 **중간 과정을 설명하는 서사 구조**라서, 첫 번째 숫자만 뽑는 휴리스틱이 중간 단계 숫자를 "정답"으로 착각했다.

### OLD iter3 step0 (역시 휴리스틱이 "오류"로 잡은 케이스)

```json
{
  "correct_index": 1,
  "choices": [
    "참조 횟수가 1로 유지된다",
    "참조 횟수가 2로 증가한다",
    "참조 횟수가 0으로 감소한다",
    "참조 횟수가 임의로 설정된다"
  ],
  "explanation": "객체가 생성되면 참조 횟수는 1입니다. 다른 변수가 같은 객체를 참조하면 횟수가 증가합니다. 따라서 ref 변수가 obj를 참조하면 참조 횟수는 2로 증가합니다."
}
```

같은 패턴. 휴리스틱이 "횟수는 1"에서 정답=1을 뽑았는데, `choices[1]`에는 "1"이 안 들어있으니 오류로 기록. **실제로는 completely 정답이다** — `correct_index=1`이 가리키는 "참조 횟수가 2로 증가한다"가 진짜 맞는 답.

### OLD iter19 step1 — 숫자형에서도 같은 문제

```json
{
  "correct_index": 1,
  "choices": ["0", "1", "2", "3"],
  "explanation": "obj의 참조 횟수는 2에서 1로 감소합니다."
}
```

"2에서 1로 감소"에서 휴리스틱이 **먼저 등장하는 "2"**를 잡음. 근데 실제 답은 감소 이후의 **"1"**. `choices[1]='1'`, `correct_index=1` → **정답**. 또 false positive.

## 남은 2건의 진짜 NEW 버그 — 가설 수정

NEW의 실제 오류 2개는 iter5 step1과 iter8 step1.

```json
// iter5 step1
{
  "correct_index": 2,
  "choices": ["1", "2", "3", "4"],
  "explanation": "a와 b가 서로 참조하기 때문에 각 객체의 참조 횟수는 2입니다."
}

// iter8 step1
{
  "correct_index": 2,
  "choices": ["1", "2", "3", "4"],
  "explanation": "다른 변수가 같은 객체를 참조하면 횟수가 증가합니다. a와 b는 서로 참조하기 때문에 각자의 참조 횟수는 2입니다."
}
```

패턴이 똑같다. **choices=['1','2','3','4']에서 정답이 "2"인데 correct_index=2로 찍음** (정상이면 `choices[1]='2'`이니 correct_index=1).

단순 "correct_index=2 앵커링"이 아니었다. 더 정확한 가설은:

> **choices 값이 1부터 시작하는 배열(`['1','2','3','4']`)에서 정답이 "2"일 때, LLM이 "값 2"와 "배열의 2번째 위치"를 혼동한다.**

이건 사실 프롬프트에 넣은 예시와 **다른 상황**이다. 예시는 `['0','1','2','3']`로 값과 인덱스가 일치하는 케이스였고, 실제 LLM이 만들어낸 choices는 `['1','2','3','4']`로 값이 1 shift되어 있다. 그 상황에서 혼동이 생긴 것.

2건이라는 표본이 너무 작아서 체계적 bias라 단정하긴 어렵다. 하지만 두 건 모두 같은 상황(shifted choices)에서 같은 방식으로 틀렸다는 건 우연보다는 패턴에 가깝다.

## 휴리스틱의 근본 문제

이번에 드러난 가장 큰 문제는 프롬프트가 아니라 **검증 휴리스틱 자체**다.

`extract_answer_from_explanation`은 explanation에서 **첫 번째로 매치되는 숫자**를 정답으로 뽑는다. 근데 이 프롬프트가 생성하는 explanation은 대부분 **서사 구조**다:

> "객체가 생성되면 참조 횟수는 **1**입니다. 다른 변수가 참조하면 증가합니다. 따라서 최종적으로 **2**가 됩니다."

진짜 정답은 마지막 숫자인데 휴리스틱은 첫 숫자를 집음. 그래서 서사형 설명이 많은 이 프롬프트에서는 **휴리스틱이 자주 잘못 채점**한다.

false positive 3개 (OLD) + 3개 (NEW) = 전체 "오류"의 75%가 가짜였다는 소리다. 이 수치로 프롬프트 우열을 논하는 건 위험하다.

## 수정된 결론

**원래 가설:** NEW 프롬프트는 descriptive 오류를 잡았지만 example leakage로 numeric 오류를 만들었다.

**데이터를 더 보고 난 뒤:**

1. **descriptive 개선은 사실 허상이다.** OLD도 2건 모두 false positive였음. 실제로는 OLD도 descriptive 오류 0건. 그러니까 "NEW가 descriptive를 개선"이 아니라 **"descriptive는 원래 문제가 아니었다"**가 정확하다.
2. **numeric 회귀는 부분적으로 진짜다.** 실제 2/12 ≈ 17%, OLD는 0/12. 패턴은 shifted choices에서의 value-index 혼동.
3. **휴리스틱 신뢰도가 낮다.** 서사형 explanation에서 첫 숫자만 뽑는 게 근본 문제. 이걸 고치지 않으면 다음 실험도 똑같이 오염된다.

## 휴리스틱 개선 + 재분석 (API 호출 0)

### 휴리스틱 v2

`extract_answer_from_explanation`을 두 단계로 개편.

```python
def extract_answer_from_explanation(explanation: str) -> str | None:
    # 1순위: 결론 지시어 뒤의 숫자
    conclusion_patterns = [
        r"(?:따라서|결국|최종적으로|최종|결론적으로|그러므로|즉)[^\n]*?(\d+)",
        r"정답은\s*[\"']?(\d+)",
        r"답은\s*[\"']?(\d+)",
    ]
    for pat in conclusion_patterns:
        matches = re.findall(pat, explanation)
        if matches:
            return matches[-1]  # 여러 개면 마지막 채택

    # 2순위: 서술 패턴 — 마지막 매칭
    legacy_patterns = [...]
    last_hit = None
    for pat in legacy_patterns:
        for m in re.finditer(pat, explanation):
            last_hit = m.group(1)
    return last_hit
```

포인트는 두 가지.

- **결론 지시어 우선**: "따라서/결국/최종적으로" 뒤에 숫자가 있으면 그걸 신뢰. 서사형 explanation은 보통 이런 접속사로 마무리한다.
- **마지막 매칭 채택**: 결론 지시어가 없을 때는 기존 패턴을 모두 돌리되, 첫 매칭이 아니라 **마지막 매칭**을 쓴다. 서사 구조에서 결론은 보통 끝에 온다.

### 재분석 스크립트

`search/experiments/reanalyze.py` 신규 추가. 기존 JSONL을 읽어 개선된 `check_step`을 다시 돌리고 OLD/NEW 오류율을 재계산한다. API 호출 없음.


### 결과

`baseline_20260417_150110.jsonl`(40 레코드)을 재분석하니 숫자가 완전히 달라졌다.

| 버전 | 원래 휴리스틱 | 개선된 휴리스틱 | False positive 비율 |
|---|---|---|---|
| OLD | 13.6% (3/22) | **4.3% (1/23)** | 약 67% (3개 중 2개가 허위) |
| NEW | 17.9% (5/28) | **9.7% (3/31)** | 약 40% (5개 중 2개가 허위) |

- Part 2의 "75% false positive" 가설이 대체로 확인됨 — 실제로 OLD 쪽은 67%, NEW 쪽은 40%가 허위였다. (전수 수동 검증 때 봤던 3개 false positive 중 일부는 개선된 휴리스틱도 여전히 보수적으로 판단해서 `skipped`로 빠졌기 때문에 "오류"에서 제외되었고, 그래서 수치가 조금 다르다.)
- **NEW가 OLD보다 나쁘다**는 방향성은 그대로. 그리고 그 간극이 4.3%p에서 **5.4%p(4.3% → 9.7%)**로 오히려 벌어졌다.

### 스킵이 왜 이렇게 많은가 — 병목은 한 곳

휴리스틱 v2로 개선된 이후 스킵은 4개만 줄었다 (110 → 106). 전체 step의 66%가 여전히 스킵. "스킵이 많으면 통계가 약해지니까 이걸 먼저 줄여야 하는 거 아닌가?"라는 질문이 자연스럽게 생겼다.

스킵 사유를 네 가지로 분류해서 세어봤다.

| 사유 | OLD | NEW | 뜻 |
|---|---|---|---|
| `extract_none` | 55 (96%) | 48 (98%) | `extract_answer_from_explanation`이 None 반환 |
| `no_match_in_choices` | 2 (4%) | 1 (2%) | 정답 추출은 했지만 어떤 choice에도 그 숫자가 없음 |
| `multiple_match` | 0 | 0 | 복수 choice에 정답 포함 (판단 보류) |
| `structure_incomplete` | 0 | 0 | `correct_index` 또는 `choices` 누락 |

결론: **스킵의 97%는 딱 한 곳에서 나온다** — `extract_answer_from_explanation`이 None을 반환하는 케이스. 원인은 명확하다. 이 함수는 정규식으로 explanation에서 "정답 숫자"를 뽑는데, LLM이 생성한 explanation이 패턴과 안 맞는 서술형인 경우가 많다.

예를 들어 python_gc 쿼리인데도 LLM이 이런 식으로 쓴다.

> "객체가 참조되면 카운트가 증가하므로 참조 횟수가 올라갑니다."

메커니즘만 설명하고 **구체 숫자를 결론 문장으로 안 써주는 것**. 이런 경우 정규식은 아무것도 못 잡는다.

### 커버리지 확장은 지금 안 하는 이유

스킵률을 낮추는 방법은 있다 — 추출 패턴을 넓히거나(숫자 외에 keyword 매칭 추가), 판단 보류 분기를 적극적으로 정답 특정하는 쪽으로 바꾸거나. 근데 지금 이걸 하기엔 위험이 크다.

1. **Precision을 희생시킬 수 있다.** 방금 75%가 false positive였다는 걸 확인한 상황이다. 패턴을 넓히면 이 비율이 다시 올라갈 가능성이 높다. 커버리지 ↑ ≠ 정확도 ↑.
2. **검증된 샘플은 이미 충분하다.** 54건(OLD 23 + NEW 31) + 의심 패턴 3건 모두 shifted choices + numeric으로 일관됨. 샘플 수를 더 늘리는 것보다 이 패턴을 직접 겨냥한 v2 실험이 정보량이 더 크다.
3. **먼저 고칠 건 프롬프트다, 휴리스틱이 아니다.** 휴리스틱을 계속 튜닝하면 "검증 도구를 만들다가 프로덕트 문제를 잊어버리는" 함정에 빠지기 쉽다. 지금은 휴리스틱이 "충분히 좋다"고 선을 긋고 실제 문제로 넘어갈 때.

즉 커버리지는 "언젠가 예산이 풀리거나 gold set을 만들 때" 다시 오는 문제로 남겨두고, 지금은 프롬프트 v2로.

---

### 실제 NEW 오류 3건 — 가설 재확인

재분석으로 잡힌 NEW의 오류는 전부 같은 패턴이었다.

```
iter5 step1: correct_index=2, choices=['1','2','3','4'], 정답='2' (choices[1]이 맞음)
iter7 step0: correct_index=2, choices=['1','2','3','4'], 정답='1' (choices[0]이 맞음)
iter8 step1: correct_index=2, choices=['1','2','3','4'], 정답='2' (choices[1]이 맞음)
```

3건 모두 **`correct_index=2`, `choices[2]='3'`**. Part 2에서 세운 "shifted choices에서의 value-index 혼동" 가설이 3건으로 재현된 셈이다. (Part 2에서 본 2건 + 재분석으로 확인된 1건 추가.)

참고로 OLD에서 잡힌 1건도 같은 패턴의 반대 방향이다.

```
OLD iter19 step1: correct_index=1, choices=['0','1','2','3'], 정답='2' (choices[2]가 맞음)
```

"정답 값"과 "인덱스"를 혼동해서 한 칸 밀린 형태. 프롬프트에 관계없이 이 혼동은 base 모델에서 일정 확률로 나타난다는 뜻.

### 프롬프트 v2 방향 재설정

원래 가설("correct_index=2 앵커링")은 기각에 가깝다. 개선된 휴리스틱으로 봐도 실제 NEW 오류 3건 모두 `correct_index=2`이긴 하지만, 모두 **shifted choices(`['1','2','3','4']`) + 정답이 "2"인 상황**이다. 즉 예시 문장의 "correct_index는 2"를 따라한 게 아니라, **choices 값이 1부터 시작할 때 LLM이 혼동**하는 것.

이걸 반영한 v2 프롬프트 방향은:

- 예시를 **shifted choices 형태**로 교체하거나 추가. `choices가 ["1","2","3","4"]이고 정답이 "2"이면 correct_index는 1입니다 (choices[1]="2").` 같은 문장을 넣어 정확히 이 상황을 짚는다.
- 가능하면 **value와 index를 분리해서 체크**하는 단계를 명시적으로 추가. "correct_index를 쓰기 전에 `choices[correct_index]`가 정답 값과 같은지 확인하세요." 같은 self-check 문장.

샘플 수가 3건이라 여전히 통계적으로는 약하다. v2 실험 시에는 먼저 numeric choices가 shifted로 나오는 쿼리(python_gc, binary_search)로만 20회 이상 돌려서 이 패턴이 유의미하게 줄어드는지 확인한 뒤, 넓은 쿼리로 regression 돌리는 순서가 좋겠다.

### 이 단계에서 배운 것

- **휴리스틱 v2는 무료였다.** API 호출 없이 기존 JSONL만으로 기준선이 완전히 재구성됐다. 비싼 실험 전에 값싼 재분석을 먼저 돌려보는 패턴이 확실히 유효하다.
- **방향은 같지만 크기는 다르다.** 원래 결과에서 "NEW가 4.2%p 나쁘다"던 것이 재분석 후 "5.4%p 나쁘다"로 바뀌었다. 결론은 유지되지만 숫자를 인용할 때는 재분석 쪽을 써야 한다.
- **가설이 더 뾰족해졌다.** "example leakage로 correct_index=2 앵커링"이라는 막연한 가설이 "shifted choices에서 value-index 혼동"이라는 더 테스트 가능한 가설로 좁혀졌다. 프롬프트 v2는 이걸 직접 겨냥할 수 있다.

## 프롬프트 v2 실험 — shifted choices 정조준

### 프롬프트 변경점 (v1 → v2)

v1 (구 NEW):
```
⚠️ correct_index 규칙:
- correct_index는 choices 배열의 0-based 인덱스입니다.
- choices[correct_index]의 값이 실제 정답과 반드시 일치해야 합니다.
- 예: choices가 ["0","1","2","3"]이고 정답이 "2"이면 correct_index는 2입니다.
- 정답 값(value)과 인덱스(index)를 혼동하지 마세요.
```

v2:
```
⚠️ correct_index 규칙 (반드시 준수):
- correct_index는 choices 배열의 0-based 인덱스입니다. (첫 요소 = 0)
- choices[correct_index]의 값이 정답 값과 정확히 같아야 합니다.
- 정답 '값(value)'과 '인덱스(index)'는 다릅니다.
  특히 choices가 1부터 시작하는 경우 헷갈리기 쉬우니 아래 예시를 반드시 확인하세요.

  예 A: choices=["1","2","3","4"], 정답 값="2"
        → choices[1]="2" → correct_index = 1 ✅
        → choices[2]="3" → correct_index = 2 는 틀림 ❌

  예 B: choices=["1","2","3","4"], 정답 값="1"
        → choices[0]="1" → correct_index = 0 ✅

- correct_index를 정한 뒤, choices[correct_index]를 꺼내서 정답 값과 같은지 다시 확인하세요.
```

세 가지 변경.

1. **예시를 shifted choices(`["1","2","3","4"]`)로 교체.** v1 예시는 `["0","1","2","3"]`로 값과 인덱스가 같은 "쉬운" 케이스였다. 실제 버그는 값과 인덱스가 다른 shifted 케이스에서 나므로, 그 상황을 정면으로 시연한다.
2. **✅/❌ 양쪽 명시.** "correct_index = 1 ✅" 옆에 "correct_index = 2 는 틀림 ❌"을 붙여서 잘못된 패턴 자체를 프롬프트 안에서 배제한다.
3. **self-check 지시 추가.** "정한 뒤, choices[correct_index]를 꺼내서 정답 값과 같은지 다시 확인하세요" — LLM이 자기 검증 단계를 거치도록 유도.

### 실험 설계

예산을 절약하기 위해 **v1 데이터는 재사용**(`baseline_20260417_150110.jsonl`). v2만 새로 20회 실행.

- 쿼리: `python_gc` (v1의 오류 3건이 모두 여기서 나왔으므로 재현 확인용으로 적합)
- 프롬프트: v2 한 종류
- 반복: 20회 (v1 NEW와 동일 조건)
- **총 20 calls** (일일 예산 절반만 사용)
- 저장 파일: `results/v2_<ts>.jsonl`
- 스크립트: `search/experiments/validate_v2.py` 신규 추가

### 결과

| 버전 | 오류 step | 검증 step | 오류율 |
|---|---|---|---|
| OLD | 1 | 23 | 4.3% |
| v1 (NEW) | 3 | 31 | **9.7%** |
| **v2** | **1** | **30** | **3.3%** |

- **v2가 v1 대비 6.4%p 개선**. shifted choices 가설을 겨냥한 프롬프트 수정이 실제로 작동했다.
- **v2가 OLD보다도 살짝 낫다** (4.3% → 3.3%). "프롬프트 안 건드리는 게 낫다"는 가능성도 v2로 뒤집힘.
- 오류 패턴 분포도 바뀜 — v1은 iter5/7/8 (초반 집중), v2는 iter18 한 건 (끝자락). 초반에 몰렸던 오류가 사라졌다.

### 남은 1건

```
v2 iter18 step1: correct_index=2, choices=['1','2','3','4'], 정답='2'
                  (정답은 choices[1]에 존재)
```

여전히 같은 shifted 패턴. **완전 제거는 아니고, 빈도만 내림**. 프롬프트로 확률을 낮출 순 있어도 0으로 만들 순 없다는 것 — LLM의 value-index 혼동은 base 모델 레벨에서 일정 확률로 잔존한다.

### 한계

- 표본 1건으로 "완전히 해결"이라 단정 못한다. 20회 더 돌리면 2~3건 나올 수도 있음.
- `python_gc` 단일 쿼리. 다른 numeric 쿼리(`binary_search`, `http_redirect`)에서도 개선이 유지되는지, 반대로 v2가 다른 쿼리를 악화시키진 않는지는 **regression 실험으로 따로 확인 필요**.
- descriptive 쿼리는 OLD/v1/v2 모두 0건이라 개선 측정 불가. (원래부터 descriptive는 문제가 아니었음.)

### 이 단계에서 배운 것

- **가설이 맞으면 수치가 증명한다.** "shifted choices에서의 혼동" 가설이 맞다면 v2가 개선되어야 하고, 실제로 6.4%p 감소했다. 이게 맞으면 이런 결과가 나온다는 대응이 데이터로 확인되면 가설의 신뢰도가 크게 올라간다.
- **프롬프트는 확률을 움직일 뿐이다.** v2로 오류율이 9.7% → 3.3%가 됐지만 0은 아니다. LLM 기능의 품질은 "제거"가 아니라 "감소"의 언어로 말해야 한다. 프로덕션에서는 이 잔존 확률 위에 추가 방어선(예: 생성 후 `choices[correct_index]` 검증 로직)을 두는 게 합리적.
- **예산을 아낀 게 직접 유효하게 쓰였다.** v1은 재사용하고 v2만 20 calls로 돌렸다. 남은 20 calls로 내일 regression을 돌릴 수 있다. 설계 초기에 "예산이 설계를 결정한다"고 적었던 선택이 여기서 구체적 이득으로 돌아왔다.

# Part 3. 정리

## 이번 작업에서 얻은 것

프롬프트 검증 스크립트 2개가 전부가 아니다. 더 큰 건 몇 가지 메타적인 감각이다.

**1. "테스트의 목적과 형태가 맞는지 늘 의심해야 한다."**

- pytest에 있으니까 pytest 문법을 쓴다 → 목적엔 안 맞는다
- 한 번 짠 검증 로직은 유지한다 → 재검토하면 구멍이 보인다
- 통계 가져다 쓰면 엄밀해 보인다 → N이 작으면 그냥 노이즈다

**2. "결과가 이상하면 원시 데이터를 봐라."**

이번에 가장 크게 작동했다. 리포트 숫자만 보고 v2 프롬프트 작업에 바로 들어갔으면 존재하지도 않는 문제(example leakage)를 고치느라 엉뚱한 방향으로 튜닝했을 가능성이 매우 컸다. JSONL에 호출별 원시 응답을 다 저장해두길 잘했다.

**3. "검증 코드에도 버그가 있다. 검증 코드의 검증이 필요하다."**

이상적으로는 *수동 라벨링한 소규모 gold set*으로 휴리스틱의 정확도(precision/recall)를 먼저 측정한 뒤 실험해야 맞다. 예산 제약 때문에 N=20 기반으로 판단하는데, false positive rate가 높으면 N이 작을수록 노이즈가 결론을 지배한다. **휴리스틱 품질 ≠ 프롬프트 품질**이라는 걸 뼈저리게 느낀 실험이었다.

**4. "LLM 기반 기능은 검증 자체가 하나의 엔지니어링 문제다."**

LLM은 결정적이지 않아서 일반 단위 테스트로는 품질을 말할 수 없다. 그래서 *통계적 비교* + *휴리스틱 검증* + *수동 샘플 확인*의 조합이 필요하고, 각 층이 어떤 한계를 가지는지 인지하면서 써야 한다. 완벽하진 않지만, 이 구조가 있으면 앞으로 프롬프트 만질 때 근거를 들고 만지게 된다. 그 차이가 제일 크다.
