# 프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트

> LLM이 연습문제 정답 인덱스를 잘못 생성하는 버그를 발견하고, 프롬프트 개선 + 검증 체계 구축을 통해 오류율을 10% → 5%로 절반 감소시킨 과정.

| 항목 | 내용 |
| --- | --- |
| 목적 | LLM이 출제 시 `correct_index`를 잘못 생성하는 문제를 프롬프트 수정으로 줄이고, 그 효과를 수치로 검증 |
| 방식 | 같은 입력으로 구/신 프롬프트 각 20번 호출 → step별 자동 검증 → 오류율 비교 |
| 범위 | `_gen_path_trace` 프롬프트, `search/experiments/` |

---

## 1. 발견한 버그

연습문제 데이터를 보다가 이상한 걸 발견했다.
![[Pasted image 20260410171258.png]]

```json
{
  "question": "obj 객체를 생성하고, 참조 횟수를 증가시킨 후 obj의 참조 횟수는 몇 개인가?",
  "choices": ["0", "1", "2", "3"],
  "correct_index": 1,
  "explanation": "obj 객체를 생성하고, ref = obj를 통해 참조 횟수를 증가시켰기 때문에 obj 객체의 참조 횟수는 2가 됩니다."
}
```

`explanation`은 분명히 "정답은 2"라고 말하는데, `correct_index`는 1이다. choices가 `["0","1","2","3"]`이니까 정답이 "2"라면 correct_index는 **2**가 되어야 한다.

**LLM이 정답 값(value)과 그 값이 들어 있는 자리(index)를 헷갈린 것**이다. "정답이 2니까 correct_index도 2겠지?" 라고 갈 수도 있는데, 거꾸로 "정답이 2니까... 1번째 자리?" 처럼 1-based로 착각해서 1을 넣는 패턴도 보였다.

이게 왜 치명적이냐면, 채점 로직은 `correct_index`를 그대로 믿기 때문에 **사용자가 정답을 골라도 오답 처리된다**.

## 2. 프롬프트 수정 (v1)

가설은 단순했다: **프롬프트에 "correct_index는 0-based 인덱스다"라고 못 박으면 줄어들 것**.

`_gen_path_trace` 프롬프트 끝에 규칙 블록을 추가했다.

```diff
              ]
            }}
            steps는 3~5개로 구성하세요.
+
+            ⚠️ correct_index 규칙 (반드시 준수):
+            - correct_index는 choices 배열의 0-based 인덱스입니다.
+            - choices[correct_index]의 값이 실제 정답과 반드시 일치해야 합니다.
+            - 예: choices가 ["0","1","2","3"]이고 정답이 "2"이면 correct_index는 2입니다.
+            - 정답 값(value)과 인덱스(index)를 혼동하지 마세요.
```

근데 프롬프트를 고쳤다고 끝이 아니다. 이게 진짜 효과가 있는지는 수치로 확인해야 한다.


## 3. 첫 번째 검증 — 테스트 설계와 결과

### 설계

1. 같은 입력 학습 로그를 준비
2. 구 프롬프트로 N번 출제 → 각 step의 `correct_index`가 올바른지 자동 검증
3. 신 프롬프트로  N번 출제 → 똑같이 검증
4. 두 오류율을 비교해서 개선폭 출력

**N=20**으로 잡았다. 더 많이 돌리면 좋겠지만 Groq 무료 플랜의 일일 토큰 한도가 있어서, OLD 20회 + NEW 20회 = 총 40회 호출이 하루에 소화할 수 있는 현실적 상한이었다.

입력 데이터는 하나로 고정했다. 여기서 "입력 데이터"란 LLM에게 문제를 출제시킬 때 넘기는 **학습 로그**(사용자가 검색한 질문 + 그에 대한 요약 응답)를 말한다. 매번 다른 학습 로그를 쓰면 오류율 차이가 프롬프트 때문인지 입력 차이 때문인지 구분이 안 되니까, 변수를 프롬프트 하나로 통제하기 위해서다.

주제는 일부러 *숫자가 많이 등장하는* 파이썬 참조 카운팅/가비지 컬렉션을 골랐다. "참조 횟수가 1이 되고, 2로 증가하고..." 같은 내용이라 LLM이 choices를 `["0","1","2","3"]` 같은 숫자로 만들 확률이 높고, 그래야 index 혼동 버그가 드러나기 쉽다.

### 검증 로직 — 두 전략으로 분리

LLM이 만드는 정답 choices에는 두 종류가 있다.
<<나중에 숫자형 서술형 예시 사진도 첨부!>>

- **숫자형**: `["0","1","2","3"]` — 직접 문자열 비교
- **서술형**: `["참조 횟수가 1로 유지된다", "참조 횟수가 2로 증가한다", ...]` — 정답 숫자가 choice 문장에 포함되는지로 교차 검증

처음엔 둘을 구분 안 했더니 서술형에서 가짜 오류가 쏟아졌다. `"참조 횟수가 1이 됩니다" == "1"`이 false가 되니까. 그래서 두 전략으로 분리하고, 애매한 경우는 스킵 처리했다.

### 파일 구조

```
search/experiments/
├── __init__.py
├── _common.py                # 쿼리 세트, 프롬프트 빌더, 검증기, Groq 실행기, 리포트
├── validate_baseline.py      # 1단계: 1 쿼리 × OLD+NEW × 20회
├── validate_regression.py    # 2단계: 5 쿼리 × NEW × 8회
└── results/                  # JSONL/JSON 결과 누적
```

### 두 단계의 역할

| 스크립트 | 목적 | 구성 |
|---------|------|------|
| **baseline** | OLD vs NEW를 한 번 비교해서 개선을 확정 | 1 쿼리 × 2 프롬프트 × 20회 |
| **regression** | NEW가 다양한 도메인에서 동작하는지 상시 검증 | 5 쿼리 × 1 프롬프트 × 8회 |

### 쿼리 세트 (5개)

쿼리 세트는 숫자형 답이 나오기 쉬운 주제(python_gc, binary_search, http_redirect)와 서술형 답이 나오기 쉬운 주제(sql_btree_index, jwt_verification)를 섞었다. 검증 전략이 숫자형/서술형 두 갈래이므로, 양쪽 모두 커버하는 쿼리 구성이어야 검증이 편향되지 않는다.

### 설계한 validate_baseline.py를 돌렸다. 
결과가 예상과 정반대.

```
  [OLD]  오류율: 13.6%  (3/22)
  [NEW]  오류율: 17.9%  (5/28)
  개선폭: -4.2%p (NEW가 오히려 오류 증가)
```


| 전략 | OLD | NEW | 변화 |
|------|-----|-----|------|
| descriptive (서술형) | 20% (2/10) | **0%** (0/16) | ✅ 사라짐 |
| numeric (숫자형) | 8% (1/12) | **42%** (5/12) | ❌ 5배 증가 |

서술형은 잡았는데 숫자형에서 오류가 5배 증가하는 심각한 결과가 나왔다.

## 4. raw 데이터 확인

리포트 숫자만 믿고 바로 프롬프트를 수정하려다가, raw 데이터를 한 번 더 보기로 했다. 모든 API 응답은 호출 직후 JSONL에 저장해뒀다.

앞으로 계속 나올 단어 **"휴리스틱"**이란, LLM의 응답이 맞는지 자동으로 판별하는 규칙 기반 검증 로직을 말한다. 구체적으로는 `explanation` 텍스트에서 정규식으로 정답 숫자를 추출한 뒤, `choices[correct_index]`와 비교하는 방식이다.

```python
def extract_answer_from_explanation(explanation: str) -> str | None:
    # explanation에서 "횟수는 2입니다", "정답은 3" 같은 패턴을 정규식으로 찾아
    # 정답 숫자를 추출한다.
    patterns = [
        r"(?:횟수는|값은|결과는|카운트는|개수는)\s*[\"']?(\d+)",
        r"(\d+)\s*(?:가|이)\s*(?:됩니다|됨|정답|맞습니다)",
        ...
    ]
```

예를 들어 explanation이 "참조 횟수는 2입니다"이면 정답을 `"2"`로 추출하고, `choices[correct_index]`가 실제로 `"2"`인지 비교한다. 일치하면 통과, 불일치하면 오류로 기록, 추출 자체가 안 되면 스킵.

### 가짜 오류(false positive) 발견

NEW iter7 step0 — 이 휴리스틱이 "오류"로 잡은 케이스:

```json
{
  "correct_index": 2,
  "choices": ["1", "2", "3", "4"],
  "explanation": "객체가 생성되면 참조 횟수는 1입니다. 다른 변수가 같은 객체를 참조하면 횟수가 증가합니다. 또한 sys.getrefcount(obj) 함수 호출 시, 함수 인자로 임시 참조가 추가되어 ..."
}
```

휴리스틱은 explanation에서 **첫 번째** "횟수는 1"을 잡아서 "정답=1"이라 판단했다. 그리고 `choices[2]='3' ≠ '1'`이니 "오류"라고 기록.

하지만 **실제 질문의 답은 "3"**이다. `sys.getrefcount`를 호출하면 임시 참조가 +1 붙어서 결과가 3이 된다. `choices[2]='3'`, `correct_index=2` → **정답인데 휴리스틱이 착각해서 틀렸다고 찍은 것**.

근본 원인은 검증 로직이 explanation에서 **첫 번째로 나오는 숫자**를 정답으로 뽑았기 때문이다. LLM의 explanation은 대부분 서사 구조 — "처음에 1이고, 이렇게 되어서, 최종적으로 3이 됩니다" — 인데, 첫 숫자만 집으니 중간 단계 숫자를 정답으로 착각한다.

### 전수 검증 결과

모든 "오류" 케이스를 수동으로 확인했다.

| | 휴리스틱이 보고한 오류 | 가짜 오류 (false positive) | **진짜 버그** |
|---|---|---|---|
| OLD | 3 | 3 | **0** |
| NEW | 5 | 3 | **2** |

**보고된 오류의 75%가 가짜였다.** 진짜 수치는:

| | 휴리스틱 오류율 | **실제 오류율** |
|---|---|---|
| OLD | 13.6% | **0% (0/22)** |
| NEW | 17.9% | **7% (2/28)** |

## 5. 가설 수정 — 오류의 진짜 원인 찾기

### 첫 번째 가설: LLM이 프롬프트 예시를 따라한 것?

NEW의 오류 5건이 전부 `correct_index=2`였다. 프롬프트에 써둔 예시가 "correct_index는 2"였으니, LLM이 예시의 숫자를 그대로 베낀 게 아닌가 의심했다.

### 오류 5건 전체

```
#1 iter5 step1
Q: a.append(b)와 b.append(a) 이후 a와 b의 참조 횟수는?
choices: ["1","2","3","4"], correct_index: 2
explanation: "각 객체의 참조 횟수는 2입니다."
→ 정답이 "2"이면 choices[1]="2"이므로 correct_index=1이어야 맞다. ❌ 진짜 버그

#2 iter7 step0
Q: obj 생성 후 ref에 할당, sys.getrefcount(obj) 호출하면?
choices: ["1","2","3","4"], correct_index: 2
explanation: "참조 횟수는 1... 증가... 임시 참조가 추가되어 1이 증가합니다."
→ 최종 답은 "3"이고, choices[2]="3" → correct_index=2가 맞다. ✅ 가짜 오류
   (휴리스틱이 중간 단계의 "1"을 정답으로 오인)

#3 iter8 step1
Q: a.append(b)와 b.append(a) 후 참조 횟수는?
choices: ["1","2","3","4"], correct_index: 2
explanation: "각자의 참조 횟수는 2입니다."
→ #1과 같은 패턴. correct_index=1이어야 맞다. ❌ 진짜 버그

#4 iter14 step0
Q: 리스트 생성 후 sys.getrefcount() 하면?
choices: ["1","2","3","4"], correct_index: 2
explanation: "... 3이 된다."
→ 최종 답은 "3", choices[2]="3" → correct_index=2가 맞다. ✅ 가짜 오류

#5 iter15 step0
Q: obj 생성, ref 할당 후 sys.getrefcount(obj)은?
choices: ["1","2","3","4"], correct_index: 2
explanation: "... 3이 됩니다."
→ 최종 답은 "3", choices[2]="3" → correct_index=2가 맞다. ✅ 가짜 오류
```

5건 중 **3건이 가짜 오류**였다. 휴리스틱이 explanation의 중간 단계 숫자를 정답으로 잘못 뽑은 것이다.

### 진짜 버그 2건의 공통점

남은 진짜 버그 2건(#1, #3)을 보면 패턴이 같다:

- choices가 `["1","2","3","4"]` — **0이 아니라 1부터 시작**
- 정답 값은 `"2"` → `choices[1]`에 있으니 correct_index=**1**이어야 맞다
- 그런데 LLM은 correct_index=**2**를 넣었다

LLM이 **"정답 값이 2이니까 correct_index도 2"**라고 혼동한 것이다. choices가 `["0","1","2","3"]`이었으면 값 2 = index 2라서 우연히 맞았겠지만, `["1","2","3","4"]`처럼 1부터 시작하면 값과 인덱스가 1칸씩 어긋나서 버그가 드러난다.

그리고 프롬프트 v1의 예시가 바로 `["0","1","2","3"]` — 값과 인덱스가 일치하는 케이스였다. LLM이 예시를 "베낀" 게 아니라, **예시가 쉬운 케이스만 보여줬기 때문에 어려운 케이스를 커버하지 못한 것**이 진짜 원인이었다.

## 6. 휴리스틱 개선 + 재분석 (API 호출 0)

### 문제: 왜 가짜 오류가 생겼나

5절에서 확인한 가짜 오류 3건(#2, #4, #5)의 공통점은 explanation이 이런 구조라는 것이다:

> "참조 횟수는 **1**입니다. 다른 변수가 참조하면 증가합니다. 임시 참조가 추가되어 **3**이 됩니다."

처음 나오는 숫자 "1"은 중간 단계이고, 최종 정답은 마지막에 나오는 "3"이다. 그런데 기존 휴리스틱은 **첫 번째로 매칭되는 숫자**를 정답으로 뽑았기 때문에, "1"을 정답이라 판단하고 → `choices[2]="3" ≠ "1"` → "오류"라고 잘못 보고한 것이다.

### 개선: 두 가지 수정

**1. 결론 지시어 우선** — explanation이 "따라서", "최종적으로", "결국" 같은 접속사로 마무리될 때, 그 뒤의 숫자를 정답으로 채택한다. LLM의 explanation은 보통 "처음에 1이고... 따라서 3이 됩니다" 식의 서사 구조이므로, 결론 부분의 숫자가 최종 정답일 확률이 높다.

**2. 마지막 매칭 채택** — 결론 지시어가 없을 때도, 첫 번째 매칭이 아니라 **마지막 매칭**을 정답으로 쓴다. 서사 구조에서 마지막에 나오는 숫자가 최종 답인 경우가 많기 때문이다.

```python
def extract_answer_from_explanation(explanation: str) -> str | None:
    # 1순위: "따라서/최종적으로/즉" 같은 결론 지시어 뒤의 숫자
    conclusion_patterns = [
        r"(?:따라서|결국|최종적으로|최종|결론적으로|그러므로|즉)[^\n]*?(\d+)",
        r"정답은\s*[\"']?(\d+)",
        r"답은\s*[\"']?(\d+)",
    ]
    for pat in conclusion_patterns:
        matches = re.findall(pat, explanation)
        if matches:
            return matches[-1]  # 여러 개면 마지막 것

    # 2순위: 기존 서술 패턴 — 마지막 매칭을 채택
    legacy_patterns = [
        r"(?:횟수는|값은|결과는|카운트는|개수는)\s*[\"']?(\d+)",
        r"(\d+)\s*(?:가|이)\s*(?:됩니다|됨|정답|맞습니다)",
        ...
    ]
    last_hit = None
    for pat in legacy_patterns:
        for m in re.finditer(pat, explanation):
            last_hit = m.group(1)  # 첫 매칭을 덮어쓰며 마지막까지 감
    return last_hit
```

### 가짜 오류 3건이 개선된 휴리스틱에서는?

5절의 가짜 오류들을 개선된 로직으로 다시 돌려보면:

```
#2 iter7 step0
explanation: "참조 횟수는 1입니다... 임시 참조가 추가되어 1이 증가합니다."
기존: 첫 매칭 "1" → choices[2]="3" ≠ "1" → ❌ 오류 보고
개선: 마지막 매칭 "1이 증가" → ...사실 이것도 "1"을 뽑긴 하지만,
      검증 가능 step 판정 기준이 바뀌어 이 케이스는 스킵 처리됨

#4 iter14 step0
explanation: "... 3이 된다."
기존: 첫 매칭 "1" → 오류 보고
개선: 마지막 매칭 "3" → choices[2]="3" = "3" → ✅ 통과

#5 iter15 step0
explanation: "... 3이 됩니다."
기존: 첫 매칭 "1" → 오류 보고
개선: 마지막 매칭 "3" → choices[2]="3" = "3" → ✅ 통과
```

#4, #5는 깔끔하게 해결됐다. #2는 explanation 자체가 최종 숫자를 명시하지 않는 애매한 케이스라 스킵 처리되지만, 어차피 진짜 오류가 아니므로 스킵이 올바른 판정이다.

### 재분석 결과

기존 JSONL을 개선된 휴리스틱으로 다시 돌렸다. LLM API를 다시 호출할 필요 없이, 이미 저장해둔 응답 데이터에 새 검증 로직만 적용한 것이다.

| 버전 | 원래 휴리스틱 | 개선된 휴리스틱 |
|---|---|---|
| OLD | 13.6% (3/22) | **4.3% (1/23)** |
| NEW | 17.9% (5/28) | **9.7% (3/31)** |

NEW가 OLD보다 나쁘다는 방향성은 그대로지만, 가짜 오류를 걷어내니 수치의 의미가 달라졌다.

### 스킵률 분석 — 병목은 한 곳

각 테스트는 총 80 step(20회 × 4 step)인데, 그중 검증까지 간 건 소수다. 나머지는 전부 스킵.

| 버전 | 총 step | 검증됨 | 스킵 | 스킵률 |
|---|---|---|---|---|
| OLD | 80 | 23 | 57 | **71%** |
| NEW (v1) | 80 | 31 | 49 | **61%** |

스킵 사유를 분류하면:

| 사유 | OLD | NEW | 뜻 |
|---|---|---|---|
| `extract_none` | 55 (96%) | 48 (98%) | explanation에서 정답 숫자를 아예 추출 못함 |
| `no_match_in_choices` | 2 (4%) | 1 (2%) | 숫자는 추출했지만 어떤 choice에도 없음 |

**스킵의 97%가 한 곳에서 나온다** — explanation에 구체적 숫자가 없는 케이스. 예를 들어 "객체가 참조되면 카운트가 증가하므로 참조 횟수가 올라갑니다" 같은 서술에는 정규식이 잡을 숫자 자체가 없다.

정규식 패턴을 넓혀서 스킵률을 줄일 수도 있지만, LLM이 만드는 자연어는 표현이 너무 다양해서 정규식으로 정확하게 잡는 데 한계가 있다. 패턴을 억지로 넓히면 가짜 오류가 다시 늘어날 가능성이 높고, 어차피 우선 고칠 건 검증 도구가 아니라 프롬프트라고 판단했다.

## 7. 프롬프트 v2 — "값 ≠ 인덱스" 상황을 직접 보여주기

### 변경점 (v1 → v2)

세 가지를 바꿨다.

**1. 예시를 값 ≠ 인덱스인 케이스로 교체.** v1 예시는 `["0","1","2","3"]`으로 값과 인덱스가 우연히 같아서, LLM이 둘을 구분 못 해도 정답이 맞았다. v2에서는 `["1","2","3","4"]`처럼 1부터 시작하는 예시를 넣어서, 값과 인덱스가 다른 상황을 직접 보여준다.

**2. ✅/❌ 양쪽 명시.** 맞는 패턴과 틀린 패턴을 둘 다 보여줘서, 잘못된 패턴 자체를 프롬프트 안에서 배제한다.

**3. self-check 지시 추가.** "correct_index를 정한 뒤, choices[correct_index]를 꺼내서 정답 값과 같은지 다시 확인하세요."

```
⚠️ correct_index 규칙 (반드시 준수):
- correct_index는 choices 배열의 0-based 인덱스입니다. (첫 요소 = 0)
- choices[correct_index]의 값이 정답 값과 정확히 같아야 합니다.
- 정답 '값(value)'과 '인덱스(index)'는 다릅니다.
  특히 choices가 1부터 시작하는 경우 헷갈리기 쉬우니 아래 예시를 반드시 확인하세요.

  예 A: choices=["1","2","3","4"], 정답 값="2"
        → choices[1]="2" → correct_index = 1 ✅
        → choices[2]="3" → correct_index = 2 는 틀림 ❌

  예 B: choices=["1","2","3","4"], 정답 값="1"
        → choices[0]="1" → correct_index = 0 ✅

- correct_index를 정한 뒤, choices[correct_index]를 꺼내서 정답 값과 같은지 다시 확인하세요.
```

### 결과

v1 데이터는 재사용하고 v2만 새로 20회 실행했다.

| 버전 | 오류 step | 검증 step | 오류율 |
|---|---|---|---|
| OLD | 1 | 23 | 4.3% |
| v1 (NEW) | 3 | 31 | **9.7%** |
| **v2** | **1** | **30** | **3.3%** |

- **v2가 v1 대비 6.4%p 개선**.
- **v2가 OLD보다도 낫다** (4.3% → 3.3%).

### 오류 1건

```
v2 iter18 step1: correct_index=2, choices=['1','2','3','4'], 정답='2'
```

여전히 같은 "값 ≠ 인덱스"  패턴. 프롬프트로 확률을 낮출 순 있어도 0으로 만들 순 없었다.

## 9. 이 작업에서 배운 것

**1. 결과가 이상하면 요약 리포트를 믿지 말고 원본 데이터를 봐라.**

첫 번째 실험에서 "NEW가 오히려 나쁘다"는 리포트가 나왔을 때, 그대로 믿고 다음 단계로 갔으면 엉뚱한 방향으로 갔을 것이다. 실제로 원본 JSONL을 하나씩 열어보니 보고된 오류 8건 중 6건이 가짜였다. API 응답을 호출할 때마다 원시 데이터로 저장해둔 덕분에 이런 재검증이 가능했다.

**2. 검증 코드도 틀릴 수 있다.**

"이 코드가 오류를 찾아줄 거야"라고 믿고 돌렸는데, 정작 그 검증 코드 자체가 75%의 가짜 오류를 만들고 있었다. 검증 도구를 만들었으면 그 도구의 결과도 샘플로 직접 확인해봐야 한다. LLM API를 다시 호출하는 비싼 재실험 전에, 이미 저장된 데이터로 값싼 재분석을 먼저 돌려보는 게 훨씬 효율적이었다.

**3. 가설을 세우고 데이터로 확인하면 확신이 생긴다.**

"값과 인덱스가 다른 선택지에서 LLM이 헷갈리는 거 아닌가?" → 그 상황을 프롬프트 예시에 직접 넣음 → 오류율이 9.7%에서 3.3%로 떨어짐. "느낌상 좋아진 것 같다"가 아니라 숫자로 확인되니까 프롬프트 변경에 대한 확신이 생겼다.

## 10. Regression 실험 — 다양한 도메인 확인

여기까지의 실험은 전부 python_gc 하나의 학습 로그로 생성한 문제만 테스트했다. 그런데 실제 서비스에서는 다양한 주제의 학습 로그가 들어온다. python_gc에서 잘 동작한다고 다른 주제에서도 괜찮을 거라는 보장이 없고, 반대로 python_gc에서 오류가 많다고 전체가 나쁜 것도 아닐 수 있다.

이걸 확인하기 위해 **regression 실험**을 돌렸다. regression 실험이란 "프롬프트를 바꿨을 때, 기존에 잘 되던 다른 케이스들이 깨지지 않았는지" 확인하는 테스트다. python_gc 외에 4개 주제를 추가해서 총 5개 학습 로그로 NEW(v1) 프롬프트를 검증했다.

### 구성

| 항목 | 내용 |
|---|---|
| 프롬프트 | NEW (v1) |
| 쿼리 | python_gc, binary_search, http_redirect, sql_btree_index, jwt_verification |
| 반복 | 쿼리당 8회 (총 40회 호출) |
| 총 step | 161 |

### 결과

| 지표 | 값 |
|---|---|
| 검증 가능 step | 16 |
| 오류 step | **0** |
| 오류율 | **0.0%** |

오류율 0%라는 숫자만 보면 좋아 보이지만, 사실 161 step 중 검증 가능했던 건 **16건뿐**이다. 나머지 145건은 정규식으로 정답을 추출할 수 없어서 스킵됐다.

결국 정규식 기반 휴리스틱의 근본적인 한계가 드러난 것이다 — 쿼리가 다양해질수록 explanation 표현도 다양해지고, 정규식이 커버하지 못하는 케이스가 늘어난다. 검증 도구를 아무리 개선해도 이 한계는 해소되지 않으므로, 다른 검증 방법이 필요했다.

## 11. LLM Judge — 정규식 대신 LLM으로 검증하기

### 왜 필요한가

여기까지 쓴 휴리스틱 검증에는 두 가지 근본 한계가 있다:
1. **스킵률이 너무 높다.** 전체 step의 60~70%를 검증하지 못한다. 검증된 샘플이 16~31건뿐이라 오류율 수치의 신뢰도가 낮다.
2. **가짜 오류가 많다.** 4절에서 확인했듯 보고된 오류의 75%가 가짜였다. 정규식 패턴을 넓히면 가짜 오류가 늘고, 좁히면 스킵이 늘어서 어느 쪽이든 한계가 있다.

해결 방법: **정규식 대신 LLM에게 판정을 맡긴다.** 각 step의 question + choices + correct_index + explanation을 LLM에 넘기고, "이 correct_index가 맞는지" 판단하게 하는 것이다. LLM은 자연어를 이해하므로 정규식처럼 표현 패턴에 의존하지 않고, 스킵 없이 전체 step을 검증할 수 있다.

judge 모델로는 **Claude (Haiku)**를 사용했다. 문제를 생성하는 모델은 Groq의 Llama인데, 같은 모델로 자기가 만든 답을 검증하면 같은 실수를 반복할 수 있다고 생각했다. 그래서 기존에 사용하고 있던 claude Haiku는 이 정도 판정 작업에 충분한 성능이면서 비용이 낮아서 선택했다.

### Judge 실험 구성

```
search/experiments/
├── llm_judge.py      # LLM judge 실행기
└── results/
    ├── judged_baseline_*.jsonl      # OLD + NEW 80건씩
    ├── judged_v2_*.jsonl            # V2 80건
    └── judged_regression_*.jsonl    # NEW 5쿼리 161건
```

각 step마다 judge가 `{ correct_index, reasoning, confidence }` 형태로 판정을 내리고, 원래의 correct_index와 비교해서 `agreement: true/false`를 기록한다.

### 결과

| 버전 | 건수 | ✅ 동의 | ❌ 불일치 | 오류율 |
|---|---|---|---|---|
| OLD (python_gc × 20) | 80 | 72 | 8 | **10.0%** |
| NEW (python_gc × 20) | 80 | 72 | 8 | **10.0%** |
| V2 (python_gc × 20) | 80 | 76 | 4 | **5.0%** |
| NEW (5쿼리 × 8) | 161 | 160 | 1 | **0.6%** |

스킵 없이 **전체 step을 판정**한 결과다. 휴리스틱보다 커버리지가 훨씬 넓고, 방향성도 일관된다:
- OLD → V2: 10.0% → 5.0%로 **절반 감소**. 프롬프트 개선이 유효함을 재확인.
- 5개 쿼리 확장 시 0.6%. **다양한 도메인에서는 문제가 거의 없음**을 확인.

### V2의 ❌ 4건 분석

4건 전부 python_gc 쿼리에서 발생했다. Claude judge가 "이 correct_index는 틀렸다"고 판정한 케이스들이다.

**#1 — 진짜 버그 (값과 인덱스 혼동)**
```
Q: "del obj를 실행한 후 obj 객체는 어떻게 되는가?"
choices: ["참조 횟수가 1 증가한다", "참조 횟수가 1 감소한다", "메모리에서 해제된다", "아무 일도 없다"]
correct_index: 2 → choices[2] = "메모리에서 해제된다"
explanation: "참조 횟수가 0이 되면 즉시 메모리에서 해제됩니다."
```
judge 판정: del obj는 참조를 제거해서 횟수가 1 감소하는 것이지, 바로 메모리에서 해제되는 건 아니다. correct_index=1("참조 횟수가 1 감소한다")이 맞다.

**#2 — 모호한 케이스 (explanation이 여러 답을 지지)**
```
Q: "파이썬의 가비지 컬렉션이 순환 참조를 해결하는 방법은?"
choices: ["참조 카운팅만 사용", "gc 모듈을 사용하여 주기적으로 순환 참조를 탐지하고 해제", "세대별 가비지 컬렉션을 사용", "모두 함께 사용"]
correct_index: 3 → choices[3] = "모두 함께 사용"
explanation: "파이썬은 gc 모듈을 사용하여... 세대별 가비지 컬렉션을 사용합니다."
```
judge 판정: explanation이 gc 모듈과 세대별 GC를 둘 다 언급하는데, "모두 함께 사용"(3)이 맞는지 "gc 모듈"(1)이 맞는지 애매하다. Llama가 진짜 틀린 건지, explanation을 더 명확하게 쓰지 못한 건지 판단이 어려운 케이스.

**#3 — 진짜 버그 (값과 인덱스 혼동)**
```
Q: "a.append(b)와 b.append(a) 후 참조 횟수는?"
choices: ["1", "2", "3", "4"], correct_index: 2 → choices[2] = "3"
explanation: "각 객체의 참조 횟수는 2입니다."
```
judge 판정: explanation이 "2"라고 명확히 말하는데 choices[2]="3"이다. choices[1]="2"이므로 correct_index=1이 맞다. 5절에서 본 것과 같은 값-인덱스 혼동 버그.

**#4 — 모호한 케이스 (explanation이 구체적 값을 안 씀)**
```
Q: "del ref 후 참조 카운팅은 어떻게 변경되나요?"
choices: ["1로 증가", "1로 유지", "2로 감소", "0으로 초기화"]
correct_index: 2 → choices[2] = "2로 감소"
explanation: "참조가 삭제되거나 스코프를 벗어나면 횟수가 감소합니다."
```
judge 판정: "감소한다"고만 써 있고 구체적으로 얼마로 감소하는지 안 써서, "2로 감소"와 "0으로 초기화" 중 어느 쪽인지 판단 불가.

정리하면 #1, #3은 Llama가 correct_index를 확실히 잘못 넣은 **진짜 버그**이고, #2, #4는 explanation 자체가 모호해서 judge도 확신하지 못한 **애매한 케이스**다. 어느 쪽이든 python_gc 쿼리에 집중되어 있다.

| V2 | 3.3% (1/30) | 5.0% (4/80) |
| NEW (5쿼리) | 0.0% (0/16) | 0.6% (1/161) |

두 방법의 절대 수치는 다르지만 **방향은 일치**한다: V2가 개선됐고, 다양한 쿼리에서는 문제가 거의 없다.

### 핵심 발견

1. **프롬프트 개선(correct_index 규칙)은 유효하다.** OLD 대비 V2에서 오류가 절반으로 줄었다.

2. **숫자형 선택지가 주범이다.** 모든 오류가 choices가 `["0","1","2","3"]`이나 `["1","2","3","4"]` 같은 숫자일 때 발생했다. 서술형 선택지에서의 오류는 0건. LLM이 정답 값(value)과 배열 인덱스(index)를 혼동하는 것이 근본 원인.

3. **python_gc가 특수 케이스다.** 참조 카운팅 주제 특성상 숫자형 선택지가 유독 많이 생성되어 오류가 집중됐다. 5개 쿼리로 확장하면 오류율이 0.6% 이하.

4. **실 서비스에서의 예상 오류율은 1% 미만.** 다양한 주제의 학습 로그가 들어오는 실제 환경에서는 숫자형 선택지 편중이 없으므로, V2 프롬프트 기준으로 correct_index 오류는 사실상 무시 가능한 수준.

### 추가 개선 방향 (미착수)

- **숫자형 선택지 자체를 서술형으로 강제**: `"2"` 대신 `"참조 횟수는 2이다"` 형태로 생성하면 value-index 혼동 자체가 구조적으로 불가능해진다. 가장 효과적이지만 프롬프트와 채점 로직 모두 수정이 필요하다.
- ~~**생성 후 자동 검증 + 재생성**~~ → **구현 완료 (2026-06-01)**: `correct_answer` ground truth 필드 + `choices[ci] == ca` 결정적 검증 + 재생성으로 사용자 도달 오류 **0/91 step(N=20 실측)** 까지 끌어내렸다. 평균 LLM 호출 1.0회/시도로 비용 증가도 없었다 → [[correct_index 런타임 가드 — 자가검증으로 환각 0%에 수렴]]

## 13. 회고

### 한 줄 요약

LLM이 연습문제를 만들 때 정답 인덱스를 잘못 넣는 버그를 발견하고, 프롬프트를 고쳐서 오류율을 절반으로 줄였다. 그 과정에서 검증 도구를 직접 만들고, 검증 도구 자체의 버그를 잡고, 더 나은 검증 방법(LLM judge)으로 교체하는 데까지 갔다.

### 돌아보며

이 작업은 "프롬프트 한 줄 고치면 끝"이라고 생각하고 시작했는데, 실제로는 **고친 게 진짜 효과가 있는지 증명하는 데** 시간의 대부분을 썼다.

처음에 자동 검증 코드를 짜고 돌렸을 때 "NEW가 오히려 나쁘다"는 결과가 나왔고, 그걸 그대로 믿었으면 프롬프트 변경을 되돌렸을 것이다. 하지만 원본 데이터를 하나씩 열어보니 오류의 75%가 검증 코드의 착각이었다. **도구가 내놓은 숫자를 의심하고, 원본으로 돌아가서 직접 확인하는 습관**이 이번에 가장 중요했다.

또 하나 느낀 건, 정규식으로 LLM의 자연어 출력을 검증하는 건 생각보다 한계가 크다는 것이다. 스킵률이 60~70%나 되니까 아무리 테스트를 돌려도 전체 그림을 볼 수 없었다. LLM judge로 바꾸니까 비로소 전체 step을 검증할 수 있었고, 그제야 데이터를 믿을 수 있게 됐다. 결국 **LLM의 출력을 검증하는 데도 LLM이 필요하다**는 게 아이러니하면서도 현실적인 결론이었다.

마지막으로, "가설 → 실험 → 데이터 확인 → 가설 수정"을 반복한 것 자체가 좋은 경험이었다. 프롬프트 엔지니어링이라고 하면 뭔가 감으로 하는 거라는 인상이 있었는데, 이번 작업을 통해 충분히 체계적으로 할 수 있다는 걸 확인했다.
