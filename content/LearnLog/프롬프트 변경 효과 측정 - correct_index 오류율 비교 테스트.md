****# 프롬프트 변경 효과 측정 - correct_index 오류율 비교 테스트

| 항목 | 내용 |
| --- | --- |
| 목적 | LLM이 출제 시 `correct_index`를 잘못 생성하는 문제를 프롬프트 수정으로 줄이고, 그 효과를 수치로 검증 |
| 방식 | 같은 입력으로 구/신 프롬프트 각 20번 호출 → step별 자동 검증 → 오류율 비교 |
| 범위 | `_gen_path_trace` 프롬프트, `search/tests/test_prompt_correct_index.py` |

---

## 발견한 버그

연습문제 데이터를 보다가 이상한 걸 발견했다.
![[Pasted image 20260410171258.png]]

```json
{
  "question": "obj 객체를 생성하고, 참조 횟수를 증가시킨 후 obj의 참조 횟수는 몇 개인가?",
  "choices": ["0", "1", "2", "3"],
  "correct_index": 1,
  "explanation": "obj 객체를 생성하고, ref = obj를 통해 참조 횟수를 증가시켰기 때문에 obj 객체의 참조 횟수는 2가 됩니다."
}
```

`explanation`은 분명히 "정답은 2"라고 말하는데, `correct_index`는 1이다. choices가 `["0","1","2","3"]`이니까 정답이 "2"라면 correct_index는 **2**가 되어야 한다.

원인이 짐작이 갔다. **LLM이 정답 값(value)과 그 값이 들어 있는 자리(index)를 헷갈린 것**이다. "정답이 2니까 correct_index도 2겠지?" 라고 갈 수도 있는데, 거꾸로 "정답이 2니까... 1번째 자리?" 처럼 1-based로 착각해서 1을 넣는 패턴도 보였다.

이게 왜 문제냐면, 사용자가 옳게 풀어도 시스템이 틀렸다고 채점하기 때문이다. `_evaluate_path_trace`는 사용자가 선택한 인덱스랑 `correct_index`를 그대로 비교하니까, 출제 단계에서 `correct_index`가 틀어져 있으면 그 문제는 영영 풀리지 않는 문제가 된다.

---

## 가설과 수정

가설은 단순했다: **프롬프트에 "correct_index는 0-based 인덱스다"라고 못 박으면 줄어들 것**.

`_gen_path_trace` 프롬프트 끝에 규칙 블록을 추가했다.

```diff
              ]
            }}
            steps는 3~5개로 구성하세요.
+
+            ⚠️ correct_index 규칙 (반드시 준수):
+            - correct_index는 choices 배열의 0-based 인덱스입니다.
+            - choices[correct_index]의 값이 실제 정답과 반드시 일치해야 합니다.
+            - 예: choices가 ["0","1","2","3"]이고 정답이 "2"이면 correct_index는 2입니다.
+            - 정답 값(value)과 인덱스(index)를 혼동하지 마세요.
```

근데 여기서 그냥 끝내면 안 됐다. **이 변경이 진짜로 효과가 있었는지** 어떻게 알지? "느낌상 좋아진 것 같다"는 포트폴리오에서 가장 약한 말이다. 그래서 효과를 수치로 보여주는 테스트를 짜기로 했다.

---

## 테스트 설계

원하는 건 단순했다.

1. 같은 입력 학습 로그를 준비
2. 구 프롬프트로 N번 출제 → 각 step의 `correct_index`가 올바른지 자동 검증
3. 신 프롬프트로 똑같이 N번 출제 → 똑같이 검증
4. 두 오류율을 비교해서 개선폭 출력

**N=20**으로 잡았다. 너무 적으면 통계적으로 의미 없고, 너무 많으면 Groq 무료 티어 일일 토큰 한도(100k)에 걸린다. 한 번 호출이 약 1500토큰이라 40번 호출이면 약 6만 토큰 — 한도 내에 들어온다.

**입력 데이터는 고정**으로 했다. 매번 다른 학습 로그를 쓰면 프롬프트 효과인지 입력 차이인지 구분이 안 되니까. 일부러 *숫자가 많이 등장하는 주제*(파이썬 참조 카운팅/가비지 컬렉션)를 골랐다. 숫자가 많아야 LLM이 인덱스 혼동을 일으킬 가능성이 높아서.

```python
FIXED_LOG = LearningLog(
    query="파이썬 참조 카운팅과 가비지 컬렉션은 어떻게 동작하나요?",
    ai_response="(... 참조 횟수가 0이 되면 즉시 해제, ...)"
)

ITERATIONS = 20
```

## 검증 로직 — 첫 번째 시도와 실패

처음엔 단순하게 짰다.

```python
def check_step(step):
    explanation = step["explanation"]
    correct_index = step["correct_index"]
    choices = step["choices"]

    # explanation에서 숫자 정답 추출 (예: "참조 횟수는 2가 됩니다" → "2")
    expected = extract_answer_from_explanation(explanation)
    if expected is None:
        return "스킵"  # 정답 추출 실패

    chosen_value = choices[correct_index].strip()
    return "OK" if chosen_value == expected else "오류"
```

돌려봤더니 결과가 이상했다.

```
오류율: 15.0%
오류 상세:
  반복 7, step 0: explanation 정답='1', choices[1]='참조 횟수가 1이 됩니다.'
  반복 18, step 0: explanation 정답='1', choices[1]='참조 횟수가 1이 됩니다.'
```

이것들은 사실 **정답이 맞다**. `choices[1]`이 "참조 횟수가 1이 됩니다"이고 explanation도 "정답은 1"이라고 했으니 일치하는 케이스다. 단지 내 비교 로직이 `"참조 횟수가 1이 됩니다." == "1"`을 false로 본 것뿐.

문제는 분명했다. **choices가 항상 숫자형이 아니다.** LLM은 때로 `["0","1","2","3"]` 같은 깔끔한 숫자 리스트를 만들지만, 때로는 `["참조 횟수가 1이 됩니다", "참조 횟수가 2로 증가합니다", ...]` 같은 서술형 문장으로 만든다.

내 첫 검증은 두 경우를 똑같이 다뤘기 때문에 서술형은 죄다 가짜 양성(false positive)을 만들어냈다.

---

## 검증 로직 — 두 전략으로 분리

choices가 숫자형인지 서술형인지에 따라 전략을 갈랐다.

### 전략 1: 숫자형 choices — 직접 비교

choices가 모두 `\d+` 패턴이면 `choices[correct_index]`의 숫자랑 explanation에서 뽑은 정답 숫자를 그대로 비교하면 된다. 이건 신뢰도가 높다.

```python
if is_numeric_choices(choices):
    chosen_num = extract_numeric(choices[correct_index])
    if chosen_num == expected:
        return OK
    else:
        # 정답 숫자가 다른 choice 자리에 있는지도 확인
        return ERROR (with "정답은 choices[X]에 존재" 정보 포함)
```

### 전략 2: 서술형 choices — 포함 여부 + 교차 검증

서술형은 단순 비교가 안 된다. 대신 두 가지를 본다.

1. `choices[correct_index]` 안에 explanation의 정답 숫자가 들어 있는가?
2. 다른 choice 중에 정답 숫자가 들어 있고, 동시에 "X가 됩니다", "횟수가 X" 같은 *정답스러운* 패턴까지 있는 게 있는가?

```
chosen에만 정답 숫자 있음           → OK
chosen에 없고 다른 choice에만 있음   → 오류 (인덱스 혼동)
양쪽 다 있음                        → 판단 보류 (스킵)
양쪽 다 없음                        → 스킵
```

이렇게 하면 서술형이라도 어느 정도 자동으로 잡을 수 있다. 다만 이 전략은 정확도를 위해 *애매하면 그냥 스킵하는* 보수적인 방향으로 갔다. 분모에서 빠지긴 하지만, 가짜 양성으로 결과를 오염시키는 것보단 낫다.

### 오류율 계산

전체 step이 아니라 **검증된 step만 분모로** 잡았다. 스킵은 분모에서도 빠진다.

```python
error_rate = error_steps / verified_steps
```

이렇게 안 하면 스킵이 많을수록 오류율이 인위적으로 낮아 보여서 비교가 망가진다.

## 한계

이 테스트엔 약점이 분명히 있다.

**1. 표본이 작다**
20회씩 돌렸지만 검증된 step은 24개/17개. LLM 출력의 분산을 고려하면 통계적 유의성을 주장하기엔 부족하다. 같은 신뢰구간 안에서 우연히 차이가 난 것일 수도 있다.

**2. 스킵률이 70%**
LLM이 서술형 choices를 자주 생성하는데, 그중에서도 *정답 숫자가 어디에도 명확히 안 드러나는* 케이스가 많아서 스킵이 늘어난다. 검증 로직을 더 정교하게 짤 수도 있지만, 정교해질수록 false positive 위험이 커진다. 보수적 스킵을 택한 트레이드오프.

**3. Groq 일일 토큰 한도**
무료 티어가 일일 100k 토큰이라, 신 프롬프트 후반 6회가 429로 실패했다. 다음에 돌릴 때는 시간 차를 두거나 429 자동 재시도 로직을 넣어야 한다.

**4. 검증 자체도 LLM 출력 의존**
explanation에서 "정답 숫자"를 정규식으로 뽑는데, LLM이 explanation을 모호하게 쓰면 추출 자체가 안 된다. 그래서 스킵이 많은 것도 일부는 이 영향이다.

## 그래도 의미 있는 점

수치는 작은 표본에 기반한 것이지만, 이 작업에서 얻은 가장 큰 건 **"프롬프트 변경의 효과를 막연한 감이 아니라 비교 가능한 숫자로 만들 수 있다"**는 패턴 자체다.

이 테스트 구조는 다른 프롬프트 변경에도 그대로 응용할 수 있다. 예를 들어:
- 답변 생성 프롬프트에서 "한자 사용 금지" 규칙을 넣었을 때, 한자가 섞여 나오는 빈도가 얼마나 줄었는지
- 인출 체크인 출제 프롬프트에서 핵심 포인트 누락률이 어떻게 변하는지

LLM 기반 기능은 결정적이지 않아서 일반적인 단위 테스트가 안 통한다. 그래서 *통계적 비교 테스트*가 또 하나의 방법이 된다는 걸 직접 만들어보면서 알게 됐다.

## 앞으로 해볼 것

- **표본 늘리기**: rate limit 풀린 다음 N=50 또는 100으로 재실행
- **429 자동 재시도**: 토큰 한도 걸리면 일정 시간 대기 후 재시도하는 래퍼 추가
- **다른 프롬프트에도 적용**: `_gen_retrieval_checkin`의 key_points 누락률, 답변 생성의 한자 혼입률 등
- **검증 로직 분리**: 지금은 테스트 파일 안에 검증 로직이 들어 있는데, 다른 테스트에서도 쓸 수 있게 `tests/utils/llm_validators.py`로 빼면 좋겠음
