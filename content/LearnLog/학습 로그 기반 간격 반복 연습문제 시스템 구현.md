## 만들게 된 계기

원래 LearnLog는 검색 → 답변 → 마크다운 저장까지의 흐름이었는데, 막상 써보니 **저장만 하고 다시 안 보게 되는** 문제가 있었다. 검색해서 답을 얻은 그 순간엔 이해한 것 같지만, 며칠 지나면 잊어버리고 같은 걸 또 검색하고 있었다.

그러던 중 아래 참고 레포지터리(DrCatHicks/learning-opportunities)를 발견했다. AI 보조 코딩 환경에서 개발자의 학습이 퇴화하는 문제를 인지과학적으로 풀어낸 도구인데, 여기서 강조하는 **Generation Effect**, **Testing Deficit**, **Spacing Effect** 같은 개념이 내가 겪던 문제와 정확히 맞아떨어졌다.

그래서 LearnLog 안에 "검색해서 저장한 내용 → 자동으로 만들어지는 나만의 연습문제"라는 흐름을 추가했다. 학습 로그 자체가 곧 문제 풀이 소스가 되도록.

---

## 요구사항

- 학습 로그 한 건마다 3가지 유형(생성→비교 / 경로추적 / 인출 체크인) 중 하나로 문제를 만들 수 있어야 한다.
- 객관식이 아닌 서술형 답변은 **AI가 채점**해야 한다. 생성→비교는 모범 답안과 비교하고, 인출 체크인은 핵심 포인트가 잘 들어갔는지 본다.
- 한 문제는 여러 번 풀 수 있고, 풀 때마다 기록(`ExerciseAttempt`)이 따로 남아야 한다.
- **간격 반복**: 맞히면 다음에 다시 풀 시점을 점점 늦추고, 틀리면 1일로 되돌린다.
- 복습 목록에는 다시 풀 시점(`next_review_at`)이 지난 문제만 보이게 한다.
- 유형마다 필요한 데이터 모양이 달라서, 고정 컬럼 말고 **JSONField**에 유형별로 자유롭게 담는다.

### 핵심 문제 의식

[https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/resources/PRINCIPLES.md](https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/resources/PRINCIPLES.md)

| 문제 | 설명 |
| --- | --- |
| Generation Effect 위험 | AI가 생성한 코드를 그냥 수용하면 능동적 처리가 줄어 기억에 안 남음 |
| Fluency Illusion | 깔끔하게 생성된 코드를 보고 이해했다고 착각함 |
| Spacing Effect 위험 | 쉬지 않고 계속 작업하면 간격을 두고 복습하는 효과를 못 누림 |
| Testing Deficit | 완성된 답을 바로 보면 인출 연습 기회가 없어짐 |

### 6가지 연습 유형

[https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/SKILL.md](https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/SKILL.md)

- 프롬프트 원문
    
    ---
    
    Generation → Comparison
    
    1. **Pause:** "Before I show you how we handle [X], sketch out how you'd approach it"
    2. Wait for response
    3. Show the actual implementation
    4. **Pause:** "What's similar? What's different, and why do you think we went this
    direction?"
    
    ---
    
    Trace the Path
    
    1. Set up a concrete scenario with specific values
    2. **Pause at each decision point:** "The request hits the middleware now. What happens
    next?"
    3. Wait before revealing each step
    4. Continue through the full path
    
    ---
    
    Retrieval Check-in
    
    At the start of a new session on an ongoing project:
    
    1. **Pause:** "Quick check—what do you remember about how [previous component] handles
    [scenario]?"
    2. Wait for response
    3. Fill gaps or confirm, then proceed

| 유형 | 설명 |
| --- | --- |
| Prediction → Observation → Reflection | 동작을 예측하고 실제 결과와 비교 후 차이를 반성 |
| ⭐️Generation → Comparison | 먼저 스스로 답을 만들고 실제 구현과 비교 |
| ⭐️Trace the Path | 코드/시스템 흐름을 단계별로 추적하며 각 단계에서 답변 |
| Debug This | 그럴듯한 버그를 제시하고 스스로 분석·수정 |
| Teach It Back | 새 팀원에게 설명하듯 개념을 직접 설명 |
| ⭐️Retrieval Check-in | 이전 세션 개념을 기억에서 꺼내는 메모리 테스트 |

### 설계 원칙

- **Pause for input is non-negotiable**: 질문 후 즉시 답을 주지 않고 반드시 학습자 입력을 기다림
- **Fading scaffolding**: 처음엔 "파일 X, N번 줄 열어보세요" → 점점 "어디를 바꿔야 할까요?"로 힌트 축소
- **세션당 최대 2개**: 강요하지 않고 동의를 구한 뒤 진행

## 어디까지 참고했나

참고 레포는 **Claude Code 플러그인** 형태라 CLI 대화 인터페이스가 전제다. LearnLog는 웹 서비스라 그대로 가져올 수 없어서, **개념과 유형 분류는 차용하되 인터랙션과 운영 방식은 웹에 맞게 재설계**했다.

### 1. 핵심 문제 의식 → 그대로 가져옴

참고 레포가 짚은 4가지 문제는 내가 LearnLog를 쓰면서 느꼈던 것과 똑같았다. 그래서 이 4가지를 LearnLog의 어떤 기능이 해결하게 할지 하나씩 짝지었다.

| 참고 레포가 말하는 문제 | LearnLog에서는 이렇게 풀었다 |
| --- | --- |
| Generation Effect 위험 (그냥 받아 적으면 기억에 안 남음) | **생성→비교** 유형: 모범 답안을 보기 전에 자기 답을 먼저 쓰게 함 |
| Testing Deficit (답을 다시 보기만 하면 인출 연습이 안 됨) | **인출 체크인** 유형: 답을 다시 보지 말고 기억에서 꺼내서 적게 함 |
| Spacing Effect 위험 (한 번에 몰아서 보면 효과가 떨어짐) | **간격 반복** 시스템 (`REVIEW_INTERVALS = [1,3,7,14,30]`)으로 시간을 두고 다시 풀게 함 |
| Fluency Illusion (깔끔한 답을 보면 이해했다고 착각함) | 저장만 하고 끝내지 않고, 연습문제로 한 번 더 인출하게 만들어서 진짜로 아는지 확인 |

### 2. 6가지 연습 유형 → 3개만 골랐다

참고 레포는 6가지 유형을 제안하는데, 그대로 다 가져오긴 어려웠다. 웹 화면 하나에서 답을 쓰고 결과를 보는 흐름이 자연스러운 것들만 골랐다.

| 원본 유형 | 골랐는지 | 이유 |
| --- | --- | --- |
| ⭐ Generation → Comparison | **채택** → `generation_compare` | 답을 한 번 쓰고 결과를 보면 끝나니까 웹 폼에 잘 맞음 |
| ⭐ Trace the Path | **채택** → `path_trace` | 객관식 스텝으로 바꾸면 한 화면에서 다 풀 수 있음 |
| ⭐ Retrieval Check-in | **채택** → `retrieval_checkin` | 답 한 번 쓰고 AI가 핵심 포인트 체크해주는 단순한 흐름 |
| Prediction → Observation → Reflection | 안 씀 | "예측하고 → 실제로 돌려보고 → 다시 생각하기"는 코드를 직접 실행할 환경이 있어야 가능 |
| Debug This | 안 씀 | 버그 코드를 만들고 학습자가 고친 걸 LLM이 제대로 채점할 수 있을지 자신이 없었음 |
| Teach It Back | 안 씀 | "동료한테 설명하듯 가르쳐라"는 대화가 여러 번 오가야 하는데, 한 번에 답을 받는 폼 구조랑 안 맞음 |

`Trace the Path`는 원래 CLI에서 한 스텝씩 답을 받으며 진행하는 방식인데, 웹에 맞게 **객관식 + JS로 즉시 피드백 + 마지막에 한 번에 제출**하는 구조로 바꿨다. "정답 보기 전에 일단 답을 골라야 한다"는 핵심 규칙(Pause for input)은 그대로 지켰다.

### 3. 설계 원칙 3개 → 1개만 적용

| 원본 원칙                              | 채택여부  | 이유                                                  |
| ---------------------------------- | ----- | --------------------------------------------------- |
| Pause for input (정답 먼저 보여주지 말 것)   | **O** | 모든 유형에서 답을 내기 전엔 모범답안/정답이 안 보이게 UI를 짰음              |
| Fading scaffolding (실력 늘면 힌트 줄여주기) | X     | 학습자 실력을 추적하는 기능이 따로 필요한데, 혼자 쓰는 MVP에 넣기엔 너무 거창함     |
| 세션당 최대 2개                          | X     | 복습 목록에서 풀고 싶은 만큼 풀 수 있게 함. 대신 간격 반복으로 자연스럽게 분산되도록 함 |

세션당 2개 제한을 굳이 안 둔 건, 두 도구의 사용 맥락이 다르기 때문이다. 참고 레포는 *Claude Code로 코딩하다가 중간에 끼어드는* 도구라서 한 번에 너무 많은 학습 활동을 끼우면 작업 흐름을 끊는다. 하지만 LearnLog는 *사용자가 일부러 복습하러 들어와서 푸는* 도구라, 개수를 막는 것보다 **다음번에 다시 풀 시점을 분산시키는 게** 더 자연스러웠다.

## 모델 설계 및 설계 의도

유형마다 필요한 데이터가 다르다. 경로추적은 객관식 선택지가 필요하고, 생성→비교는 모범 답안이 필요하고, 인출 체크인은 핵심 포인트 목록이 필요하다. 이걸 고정 컬럼으로 다 만들면 대부분 칸이 NULL로 비어 있게 된다. 그래서 `content` 컬럼 하나에 JSONField로 유형마다 다른 모양을 담기로 했다.

### Exercise

```python
class Exercise(models.Model):
    EXERCISE_TYPE_CHOICES = [
        ('generation_compare', '생성→비교'),
        ('path_trace', '경로추적'),
        ('retrieval_checkin', '인출 체크인'),
    ]

    learning_log = models.ForeignKey(LearningLog, on_delete=models.CASCADE, related_name='exercises')
    exercise_type = models.CharField(max_length=30, choices=EXERCISE_TYPE_CHOICES)
    content = models.JSONField() # 유형별 문제 데이터
    review_interval = models.PositiveIntegerField(default=1) # 현재 복습 주기 (일)
    next_review_at = models.DateTimeField(null=True, blank=True) # 다음 복습 예정일
```

- LearningLog에 FK를 건 이유: 연습문제는 특정 학습 로그에서 출발해서 만들어진 거라, 그 로그가 사라지면 문제도 같이 사라지는 게 자연스러움.

### ExerciseAttempt

```python
class ExerciseAttempt(models.Model):
    exercise = models.ForeignKey(Exercise, on_delete=models.CASCADE, related_name='attempts')
    user_answer = models.JSONField()
    is_correct = models.BooleanField(null=True, blank=True)
    ai_feedback = models.TextField(blank=True)
    score = models.FloatField(null=True, blank=True)  # 0.0 ~ 1.0
```

- Exercise랑 따로 둔 이유: 한 문제를 여러 번 풀 수 있어서 풀이 기록도 여러 개가 쌓인다. 이걸 Exercise 안에다 다 욱여넣으면 풀 때마다 JSONField가 지저분해지고, 나중에 "이 문제 몇 번 풀었지", "지난번엔 몇 점이었지" 같은 걸 보기 힘들어짐.

### JSONField content 구조

1. **생성→비교**

```json
{
  "question": "학습자에게 물어볼 질문",
  "model_answer": "모범 답안"
}
```

1. **경로추적**

```json
{
  "scenario": "추적할 시나리오 설명",
  "steps": [
    {
      "question": "이 단계에서 무슨 일이 일어나는가?",
      "choices": ["선택지A", "선택지B", "선택지C", "선택지D"],
      "correct_index": 0,
      "explanation": "왜 이것이 정답인지 설명"
    }
  ]
}
```

1. **인출 체크인**

```json
{
  "question": "기억에서 꺼내게 하는 질문",
  "key_points": ["핵심 포인트 1", "핵심 포인트 2", "핵심 포인트 3"]
}
```

## 3가지 연습문제 유형 한눈에 보기

| 유형 | 원문 | 채점 | 어떻게 푸는가 |
| --- | --- | --- | --- |
| 생성→비교 | Generation → Comparison | AI가 모범 답안이랑 비교 | 텍스트 영역에 답 쓰고 제출하면 결과 |
| 경로추적 | Trace the Path | 정답 인덱스 매칭 | 스텝마다 객관식으로 고르고, JS가 그 자리에서 맞고 틀림 표시 → 마지막에 한 번에 저장 |
| 인출 체크인 | Retrieval Check-in | AI가 핵심 포인트 빠짐 없이 들어갔는지 체크 | 텍스트 영역에 답 쓰고 제출하면 결과 |

경로추적만 JS 즉시 피드백을 쓴 이유: 스텝별로 그 자리에서 맞고 틀림을 알려줘야 학습 효과가 있고, 객관식이라 정답 인덱스만 비교하면 되니까 굳이 서버에 안 다녀와도 처리할 수 있다.

## 간격 반복 (Spaced Repetition)

맞히면 다음에 풀 시점을 점점 늦추고 (1일 → 3일 → 7일 → 14일 → 30일), 틀리면 다시 1일로 되돌리는 방식이다. 한 번 맞혔다고 영영 안 보여주는 게 아니라, 잊어버릴 때쯤 다시 꺼내서 풀게 하는 게 핵심.

```python
REVIEW_INTERVALS = [1, 3, 7, 14, 30]  # 일 단위

def advance_interval(self):
    """마지막 성공 기준으로 다음 복습일 계산"""
    idx = REVIEW_INTERVALS.index(self.review_interval)
    next_interval = REVIEW_INTERVALS[min(idx + 1, len(REVIEW_INTERVALS) - 1)]
    self.review_interval = next_interval
    self.next_review_at = timezone.now() + timezone.timedelta(days=next_interval)
    self.save(update_fields=['review_interval', 'next_review_at'])

def reset_interval(self):
    """오답 시 1일로 리셋"""
    self.review_interval = 1
    self.next_review_at = timezone.now() + timezone.timedelta(days=1)
    self.save(update_fields=['review_interval', 'next_review_at'])
```

- 기준은 **마지막으로 맞힌 시점**이다. 틀리면 그동안 쌓아둔 간격이 다 무효가 되고 1일로 돌아감.
- 복습 목록에 올라오는 조건: 한 번도 안 푼 새 문제(`next_review_at`이 비어 있음) 거나, 다시 풀 시점이 이미 지난 문제.

```python
@staticmethod
def get_due_exercises():
    return (
        Exercise.objects
        .filter(Q(next_review_at__isnull=True) | Q(next_review_at__lte=timezone.now()))
        .select_related('learning_log')
        .order_by('next_review_at', '-created_at')
    )
```

## 서비스 레이어 설계

검색·답변 생성 쪽 코드(`LearnlogService`)는 그대로 두고, 연습문제 관련은 `ExerciseService`라는 별도 클래스로 빼서 책임을 분리했다.

```
ExerciseService
├── generate_exercise(learning_log, exercise_type)  → Exercise
├── evaluate_attempt(exercise, user_answer)         → dict (is_correct, score, ai_feedback)
├── save_attempt(exercise, user_answer, evaluation) → ExerciseAttempt
└── get_due_exercises()                             → QuerySet
```

채점 방식은 유형마다 다르니까, 한 메서드 안에 if-else를 늘어놓는 대신 dispatch 딕셔너리로 깔끔하게 갈라줬다.

```python
def evaluate_attempt(self, exercise, user_answer):
    dispatch = {
        'path_trace': self._evaluate_path_trace,           # 인덱스 매칭 (AI 불필요)
        'generation_compare': self._evaluate_generation_compare,  # AI 비교
        'retrieval_checkin': self._evaluate_retrieval_checkin,    # AI 핵심 포인트 체크
    }
    return dispatch[exercise.exercise_type](exercise, user_answer)
```

### 채점 로직 상세

**1. 경로추적 — AI 없이 인덱스만 비교**

객관식이라 굳이 AI를 부를 필요가 없다. 미리 저장해둔 정답 인덱스랑 사용자가 고른 인덱스를 그냥 맞춰보면 된다. 빠르고 API 비용도 안 든다.

```python
def _evaluate_path_trace(self, exercise, user_answer):
    steps = exercise.content['steps']
    selected = user_answer.get('selected_indices', [])
    correct_count = sum(
        1 for i, step in enumerate(steps)
        if i < len(selected) and selected[i] == step['correct_index']
    )
    score = correct_count / len(steps) if steps else 0
    feedback_lines = [
        f"{'✅' if (i < len(selected) and selected[i] == step['correct_index']) else '❌'} "
        f"Step {i + 1}: {step['explanation']}"
        for i, step in enumerate(steps)
    ]
    return {
        'is_correct': score >= 0.6,
        'score': score,
        'ai_feedback': '\n'.join(feedback_lines),
    }
```

- 통과 기준은 0.6점이다. 5문제 중 3개 이상 맞히면 정답 처리. 100점이 아니면 다 틀린 걸로 치면, 한 문제만 삐끗해도 간격이 1일로 리셋돼서 너무 빡빡하다. 그러면 풀기가 싫어진다.
- 피드백은 굳이 AI를 안 거치고, 출제할 때 같이 만들어둔 스텝별 `explanation`을 그냥 이어 붙여서 보여준다.

**2. 생성→비교 — AI가 모범 답안이랑 비교**

서술형이라 단순 비교가 안 된다. 학습자의 답변과 모범 답안을 LLM한테 같이 던져주고 점수랑 피드백을 받아오는 방식.

```python
def _evaluate_generation_compare(self, exercise, user_answer):
    user_text = user_answer.get('text', '')
    prompt = textwrap.dedent(f"""
        학습자의 답변과 모범 답안을 비교하여 평가해주세요.

        질문: {exercise.content.get('question', '')}
        모범 답안: {exercise.content.get('model_answer', '')}
        학습자 답변: {user_text}

        JSON으로만 응답하세요 (```없이):
        {{
          "score": 0.0~1.0,
          "is_correct": true/false,
          "feedback": "잘한 점과 보완할 점을 한국어로 설명"
        }}
    """).strip()
    response = self.groq_client.chat.completions.create(
        model="llama-3.3-70b-versatile",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2,
        max_tokens=500,
    )
    raw = response.choices[0].message.content.strip()
    # 모델이 ```json ... ``` 으로 감싸서 반환하는 경우 방어
    if raw.startswith('```'):
        parts = raw.split('```')
        raw = parts[1] if len(parts) > 1 else raw
        if raw.startswith('json'):
            raw = raw[4:]
    result = json.loads(raw.strip())
    return {
        'is_correct': bool(result.get('is_correct', False)),
        'score': float(result.get('score', 0)),
        'ai_feedback': result.get('feedback', ''),
    }
```

- `temperature=0.2`로 낮게 잡았다. 채점은 같은 답변에 매번 같은 점수가 나와야 신뢰할 수 있다. 답변 생성 때처럼 0.7로 두면 같은 답에 점수가 들쭉날쭉해서 학습자 입장에선 혼란스럽다.
- 프롬프트에 **"JSON으로만 응답하세요 (```없이)"** 라고 못 박은 이유: LLM이 가끔 친절하게 `​` `​` `​json ... ​` `​` `​` 으로 코드블록을 씌워서 보내준다. 그러면 `json.loads`가 깨진다. 프롬프트로 1차로 막고, 그래도 감싸서 오면 코드에서 한 번 더 벗겨내는 방어 처리를 했다.
- `max_tokens=500`: 채점 결과 자체는 점수 + 짧은 피드백이라 길 이유가 없다. 토큰 비용 줄이려고 작게 잡았다.

**3. 인출 체크인 — 핵심 포인트가 다 들어갔나 체크**

이건 모범 답안 통째로 비교하지 않는다. 출제할 때 미리 "이 답에는 이런 포인트들이 들어가야 함"이라고 핵심 포인트 목록을 같이 만들어 두는데, 채점할 땐 그 포인트들이 학습자 답에 하나하나 들어갔는지를 LLM한테 체크 시킨다. 점수는 들어간 포인트 비율(예: 5개 중 3개 → 0.6점)로 계산.

```python
def _evaluate_retrieval_checkin(self, exercise, user_answer):
    user_text = user_answer.get('text', '')
    key_points = exercise.content.get('key_points', [])
    points_str = '\n'.join(f"- {p}" for p in key_points)
    prompt = textwrap.dedent(f"""
        학습자의 답변에서 핵심 포인트가 포함됐는지 확인해주세요.

        질문: {exercise.content.get('question', '')}
        핵심 포인트:
        {points_str}
        학습자 답변: {user_text}

        JSON으로만 응답하세요 (```없이):
        {{
          "covered_points": [핵심 포인트와 동일한 순서로 true/false 목록],
          "feedback": "어떤 포인트를 잘 다뤘고 무엇이 빠졌는지 한국어로 설명"
        }}
    """).strip()
    response = self.groq_client.chat.completions.create(
        model="llama-3.3-70b-versatile",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2,
        max_tokens=500,
    )
    # ... (JSON 파싱은 위와 동일) ...
    covered = result.get('covered_points', [False] * len(key_points))
    score = sum(covered) / len(key_points) if key_points else 0
    return {
        'is_correct': score >= 0.6,
        'score': score,
        'ai_feedback': result.get('feedback', ''),
    }
```

- 통째로 비교하는 대신 굳이 포인트 단위로 쪼갠 이유: "비슷한 것 같음, 0.7점" 식의 두루뭉술한 채점은 학습자가 *뭘 빠뜨렸는지*를 모른다. 인출 연습은 "아 이 부분을 까먹었구나" 를 정확히 알아야 다음에 보완할 수 있다. 그래서 어떤 포인트는 들어갔고 어떤 건 빠졌는지 명시적으로 체크하게 만들었다.
- 통과 기준은 0.6, 경로추적이랑 똑같다.

### 출제 프롬프트도 같은 패턴

문제를 만들 때 쓰는 출제 프롬프트도 채점 프롬프트랑 똑같은 방식으로 짰다. `textwrap.dedent`로 들여쓰기 깔끔하게, 응답은 JSON으로 강제. 예시 하나:

```python
def _gen_generation_compare(self, log):
    prompt = textwrap.dedent(f"""
        다음 학습 내용을 바탕으로 "생성→비교" 유형 연습문제를 만들어주세요.

        학습 내용:
        질문: {log.query}
        답변: {log.ai_response[:1000]}

        JSON으로만 응답하세요 (```없이):
        {{
          "question": "학습자에게 물어볼 질문 (핵심 개념을 직접 설명하게 유도)",
          "model_answer": "모범 답안 (핵심 포인트를 포함한 상세한 답변)"
        }}
    """).strip()
    return self._call_groq_json(prompt)
```

- `log.ai_response[:1000]`로 1000자에서 자르는 이유: 학습 로그의 AI 답변이 가끔 엄청 길어지는데, 그걸 그대로 프롬프트에 넣으면 토큰 한계에 걸리거나 API 비용이 쓸데없이 늘어난다. 문제 만드는 데는 1000자 정도면 핵심을 잡기에 충분했다.
- `_call_groq_json()`은 위 채점 코드에서 본 "JSON 파싱 + 코드블록 벗기기" 로직을 매번 복붙하지 않으려고 공용 함수로 빼놓은 것.

## 문제 생성 진입점

문제가 자동으로 만들어지진 않고 사용자가 버튼을 눌러야 생성되는 구조라, 이 버튼을 어디에 둘지 고민했다. 결국 두 군데에 뒀다.

1. **질문하고 답을 막 받은 결과 화면 아래** — 답변을 방금 본 직후가 가장 머릿속에 생생할 때라, 그때 바로 문제 만들 수 있게.
2. **학습 로그 상세 모달 아래** — 나중에 기록 보러 들어와서 "아 이거 다시 풀어볼까" 싶을 때도 만들 수 있게.

두 곳에 들어가는 버튼 HTML이 똑같길래 `partials/exercise_generate.html`로 따로 빼고 양쪽에서 `{% include %}`로 가져다 썼다.

## 프롬프트 가독성 개선

프롬프트를 그냥 f-string으로 메서드 안에 박아두면 들여쓰기가 따로 논다. 코드는 4칸 들여쓴 상태인데 프롬프트만 컬럼 0에서 시작해서 보기에 영 어색하다.

```python
# 개선 전 — 컬럼 0에서 시작해서 들여쓰기 불일치
def _gen_generation_compare(self, log):
    prompt = f"""다음 학습 내용을 바탕으로...

학습 내용:
질문:{log.query}
"""

# 개선 후 — textwrap.dedent()로 코드 들여쓰기와 통일
def _gen_generation_compare(self, log):
    prompt = textwrap.dedent(f"""
        다음 학습 내용을 바탕으로...

        학습 내용:
        질문:{log.query}
    """).strip()
```

`textwrap.dedent()`는 모든 줄의 앞에 공통으로 붙어 있는 공백을 한꺼번에 떼어주고, `.strip()`은 앞뒤로 남는 빈 줄을 정리해준다. 이렇게 하면 코드 들여쓰기는 그대로 유지하면서 LLM한테 보내지는 실제 텍스트는 컬럼 0부터 시작하는 깔끔한 형태가 된다.

## 기타 개선

**navbar 공통화**
페이지마다 navbar HTML이 똑같이 복붙되어 있었다. 이걸 `partials/navbar.html`로 따로 빼고 `base.html`에서 한 번만 `{% include %}` 하도록 정리했다. 그리고 현재 보고 있는 페이지에 해당하는 메뉴는 클릭이 안 되도록 비활성화하고 싶었는데, `request.resolver_match.url_name`으로 지금 페이지의 URL 이름을 알아낼 수 있어서 그걸로 분기했다.

```html
{% with url_name=request.resolver_match.url_name %}
    {% if url_name == 'log_list' %}
        <span class="btn btn-ghost btn-sm pointer-events-none opacity-40">질문기록</span>
    {% else %}
        <a href="{% url 'search:log_list' %}" class="btn btn-ghost btn-sm">질문기록</a>
    {% endif %}
{% endwith %}
```

**답변 프롬프트 개선**
- `max_tokens`을 2000에서 4000으로 늘렸다. 답변이 길어질 때 중간에 잘리는 경우가 있어서.
- 프롬프트에 답변 구조를 명시했다. "개념 설명 → 동작 원리 → 코드 예시 → 주의사항" 순서로 써달라고 지시. 이전엔 답변이 중구난방이었는데 구조를 잡아주니까 훨씬 학습용 자료답게 나온다.

**프롬프트 수정 기능**
메인 페이지에 "✏️ 프롬프트 수정" 토글을 달았다. 누르면 기본 지시사항이 채워진 textarea가 열리는데, 거기서 입맛대로 고친 다음 제출하면 그 지시사항대로 답변이 생성된다. 비워두면 그냥 기본값으로 동작. 같은 질문이라도 "더 짧게", "예시 위주로" 같은 톤을 직접 조절하고 싶을 때 쓰려고 만들었다.
