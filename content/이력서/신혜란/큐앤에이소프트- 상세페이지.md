- 초기 시스템 구조
    
    ![Untitled](%ED%81%90%EC%95%A4%EC%97%90%EC%9D%B4%EC%86%8C%ED%94%84%ED%8A%B8-%20%EC%83%81%EC%84%B8%ED%8E%98%EC%9D%B4%EC%A7%80/Untitled.png)
    
    - 시스템은 크게 사내포털, 주문 처리하는 서버와 증권사와 연동되어 주문을 집행하는 서버 두 가지로 나눌 수 있습니다. 데이터베이스는 서버 1개에 스키마 1개로 운영했습니다.
    - 문제점 : 정기적으로 리밸런싱(회원들의 포트폴리오 종목이나 비중 변경)을 진행하는데, 리밸런싱 할 때마다 시스템 부하가 커져서 서비스가 느려지는 것을 확인했습니다.
    - 해결시도: 정확히 어느 코드에서 느려지는지 원인을 특정하기가 어려웠고, 특정 하더라도 원인이 되는 서비스를 따로 개선하기 위해 서비스를 분리했습니다.
- 사내포털과 주문 처리 서비스 분리
    
    ![Untitled](%ED%81%90%EC%95%A4%EC%97%90%EC%9D%B4%EC%86%8C%ED%94%84%ED%8A%B8-%20%EC%83%81%EC%84%B8%ED%8E%98%EC%9D%B4%EC%A7%80/Untitled%201.png)
    
    - 문제점: django 프로젝트 및 서버를 분리한 뒤, 모니터링을 진행하여 주문 처리 서버의 부하가 큰 것을 발견했습니다
    - 해결 시도: 리밸런싱 진행에 무리 없을 수준으로 인스턴스 유형을 변경해 scale up를 하였으나, 리밸런싱을 하지 않는 경우엔 오버스펙이라 비용 측에서 비효율적이었습니다.
    - 해결: aws에서 제공하는 Elastic Load Balancing을 사용했습니다. auto scailing 대상 서버의 cpu 사용량이 기준 이상 초과할시, 서버 하나씩 생성되게 함으로서 유연하게 서버 관리를 할 수 있었습니다.
- 서비스를 분리했지만, 리밸런싱할 때 사내포털이 여전히 느린 것을 확인
    
    ![Untitled](%ED%81%90%EC%95%A4%EC%97%90%EC%9D%B4%EC%86%8C%ED%94%84%ED%8A%B8-%20%EC%83%81%EC%84%B8%ED%8E%98%EC%9D%B4%EC%A7%80/Untitled%202.png)
    
    - 문제점: 사내 포털과 주문 처리 서비스가 같은 DB를 사용하고 있어 리밸런싱 진행 시 DB부하 때문에 사내 포털도 같이 느려짐을 확인했습니다.
    - 해결: 주문처리 DB와 서버를 분리하고 인스턴스 유형을 변경해 scale up을 했습니다. 사내 포털에서도 주문 모니터링을 위해 주문처리 DB를 사용하기 때문에, django 프로젝트에 DB Routing을 사용하여 두 가지 DB를 사용할 수 있도록 조치했습니다.
- 스케쥴러를 따로 서비스로 분리
    
    ![Untitled](%ED%81%90%EC%95%A4%EC%97%90%EC%9D%B4%EC%86%8C%ED%94%84%ED%8A%B8-%20%EC%83%81%EC%84%B8%ED%8E%98%EC%9D%B4%EC%A7%80/Untitled%203.png)
    
    - 주식 주문. 모니터링 및 알람을 위해 스케쥴러(APScheduler)를 사용하고 있는데, 기존엔 내부포털 프로젝트에 같이 실행시키고 있었습니다.
    - 문제점: 내부포털 서비스는 부하 분산을 위해 배포할 때 프록시 서버로 Gunicorn worker옵션으로 로드 밸런싱을 하는데, 한 번만 실행되어야 하는 스케쥴러가 각 worker 프로세스에도 똑같이 실행되어 스케쥴러의 job들이 중복 실행되는 현상을 확인했습니다.
    - 해결: 스케쥴러를 django 프로젝트로 따로 분리하여 한 프로세스로 실행되게 조치했습니다.
- 주문용 DB를 분리하며 생긴 문제점
    - 스케쥴러는 crontab으로 동작하는 APScheduler 라이브러리를 사용하고 있었습니다.
    - 주문용 DB의 경우, 비용 절감을 위해 8시~17시 동안만 DB서버는 active 하기 때문에, 그 외의 시간에는 서버가 닫혀 있어 그동안 DB에 연결을 시도한다면 ‘DB lost connection, mysql server gone’에러가 발생합니다.
    - 문제점: 각 스케쥴러마다 고유의 thread를 생성하는데, 원래 의도는 스케쥴러의 한 트랜잭션이 종료되면 DB connection도 닫혀야 하는데, 스케쥴러의 thread가 스케쥴러를 실행시키기 위해 계속 활성되어 있어 connection이 닫히지 않고 계속 유지됩니다. 따라서 DB 서버가 닫히며 lost connection이 되고, 8시~17시 서버가 active 되어 있음에도 lost connection이 유지되어 에러가 발생했습니다.
    - 해결: 임의로 connection을 close하는 코드를 추가했습니다. 자세한 내용은 아래 페이지를 참고 부탁드립니다.
